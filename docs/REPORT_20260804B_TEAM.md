# 팀 보고 — `bf` 실측, ④ I칸 최초 실측, 그리고 **우리 GPU 계측이 부풀려져 있었다**

> **작성:** 2026-08-04 (팀원2) · **기기:** Galaxy A34 (SM-A346N, Mali-G68 MC4) · **빌드:** release
> **세션 2개:** `s5_bf`(커밋 `c2d747e`, 13런 87분) · `s6_1q`(커밋 `3bba07f`, 8런 72분)
> **동결 스냅샷이다.** 숫자가 갱신되면 `docs/baselines/` 쪽이 맞다.

## 0. 세 줄 요약

1. **`bf`(bilateral)를 이식해 쟀다.** 상류 배포 후보 `D1A1+bf`의 마지막 조각이었다.
2. 🔴 **재는 도중에 우리 계측 자체의 결함을 찾았다.** 패스별 GPU 계측(`gpu_sum_ms`)이
   프레임 하나를 **31~43% 중복 계상**한다. 패스가 많을수록 커진다.
   그래서 **기존 승격본 `D1A1 +14.526ms`도 부풀려진 값이다** — 실제는 **+9.324ms**.
3. **④ 오버레이 I칸을 처음 쟀다** — 박스 4개 기준 **+0.562ms**. 사실상 공짜다.

## 1. 🔴 계측 결함 — 먼저 읽어야 한다

### 어떻게 드러났나

`bf`를 얹은 arm에서 `gpu_sum_ms`가 **물리적으로 불가능한 값**을 냈다.

```
drago_clahe_chain_bf : 29.92fps × 43.794ms = 1310 ms/s   ← 1초에 1.31초의 GPU 작업
```

그런데 30fps가 스톨·드롭 없이 유지되고 프레임타임(p50 32.9)도 지연(`capture_to_render`
p50 76.9)도 분모와 구분이 안 됐다. 행 단위로 보면 **95.8%의 행에서 `gpu_sum`이 그 프레임의
출력 간격을 넘고** 중앙값 초과가 +10.230ms였다.

범인은 `gpu_present_ms`였다. 그 패스는 **전 arm에서 글자 그대로 같은 셰이더**(FBO→화면 blit)인데
query 값이 **1.862 → 15.078ms**로 부풀었고, 부풀림이 **마지막 전체화면 패스 비용의 73~88%**를
따라갔다. 결정적 대조군은 ④ 오버레이 arm이다 — 마지막 패스가 얇은 quad라 프래그먼트를 거의
안 건드리는데 부풀림이 **+0.010ms(2%)** 였다.

**메커니즘:** 마지막 전체화면 패스가 FBO에 쓴 것의 **타일 해결이 `present` 시점으로 미뤄지고,
그 패스의 자기 query가 이미 센 것을 `present` query가 다시 센다.**

### 실측으로 확정했다

프레임 전체를 query **하나**로 감싸는 계측 모드(`gpu_frame_ms`)를 만들어 **같은 렌더 경로**를
두 방식으로 재고 뺐다. `GL_TIME_ELAPSED`는 중첩 불가라 arm으로 갈랐다(`_1q` 접미사).

| arm | 패스 | 패스별 `gpu_sum` | 단일 `gpu_frame_ms` | **중복** | 부풀림 |
|---|---|---|---|---|---|
| `blit_2pass` | 3 | 3.709 | 2.546 | **+1.163** | 31.4% |
| `drago_clahe_chain` | 8 | 18.234 | 11.870 | **+6.364** | 34.9% |
| `drago_clahe_chain_bf` | 9 | 43.828 | 24.868 | **+18.960** | 43.3% |

단일 query로 재면 **전부 물리적으로 성립한다** — `chain_bf`가 744 ms/s(점유 75.6%)로,
30fps를 스톨 없이 유지한 관측과 모순이 없다. 패스별 값만 불가능한 값이었다.

⚠️ `chain_bf`의 단일 query 런(`#6`)에는 **런 안 드리프트가 있다**(§4). 미드리프트 기준으로
읽으면 중복이 **+19.719(45.0%)** 까지 올라간다 — 즉 위 표의 +18.960은 **중복량의 하한**이다.
`blit_2pass`·`chain`의 런은 평평했다(폭 0.006~0.009).

### 🔴 기존 승격본이 보정 대상이다

| D칸 (arm − 같은 계측의 분모) | 패스별 = **상한** | 단일 query = **하한** |
|---|---|---|
| `D1A1` (`drago_clahe_chain`) | **+14.525** | **+9.324** |
| `D1A1+bf` | +40.119 | **+22.322** |

`s6_1q`에서 패스별로 다시 잰 `D1A1`이 **+14.525**로, 승격본 **+14.526**과 **0.001ms 차이로
재현**된다. 즉 **패스별 계측은 정밀하지만 편향돼 있다.** 승격본 숫자는 재현 가능한 값이고,
동시에 부풀려진 값이다.

**아래 세 곳의 숫자가 보정 대상이다** (이 보고서에서는 고치지 않았다):
- `FRAME_BUDGET.md` §3 주6 · §6 표의 D칸
- `docs/STATUS.md` 승격 실측 표
- `docs/REPORT_20260804_TEAM.md` (동결 스냅샷이므로 그 자리에 갱신 표시만 필요)

### 두 계측을 나란히 남긴다

**하나를 지우지 않는다.** 둘 다 실측이고 뜻이 다르다:

- **패스별(`gpu_sum_ms`) = 상한.** 중복 계상을 포함한다. 어느 패스가 비싼지 알 수 있는 유일한 수단이다.
- **단일 query(`gpu_frame_ms`) = 하한.** 중복이 없다. 단 **마지막 패스의 타일 해결이
  `eglSwapBuffers`에서 일어나 여전히 query 밖이다**(알려진 이슈 2) — `GLSurfaceView`를 쓰는 한
  어떤 query로도 못 잡는다.

**진짜 값은 둘 사이에 있다.** 어느 쪽을 인용하든 **열 이름과 계측 방식을 함께 옮겨야 한다.**

## 2. `bf` — 상류 배포 후보의 마지막 조각

파라미터는 상류 원문(`Bilateral(d=7, σ_color=50, σ_space=50)`, 동작 공간 BGR)을 그대로 썼다.
`cv2.bilateralFilter` 구현을 읽어 옮겼다 — `radius = d/2 = 3`, **원형 이웃 29탭**
(7×7 사각형 49탭이 **아니다**), 색 거리는 RGB **3채널 L1 합의 제곱**, 0..255 스케일.

### 비용 (단일 query 기준 = 하한)

| | 값 | 드리프트 제외 시 (§4) |
|---|---|---|
| `D1A1` (bf 없음) | **+9.324ms** | — (그 런은 평평했다) |
| `D1A1+bf` | **+22.322ms** | +21.563 |
| **`bf` 자체** | **+12.998ms** | +12.239 |

패스별 계측으로는 `bf` 증분이 +25.594ms였다 — **절반이 중복이었다.**

### 상류 게이트 판정

상류 `data.md`의 **② ≤20ms** 기준에 대해 **`D1A1+bf`는 +22.3ms로 넘는다.** 다만 10% 초과이고,
패스별 계측으로 읽었을 때의 2배 초과와는 성격이 다르다. **`D1A1`만이면 +9.3ms로 여유가 크다.**

🔴 **단서 넷을 함께 옮겨야 한다:**
1. **"② ≤20ms"는 기획서에 없다** — 상류 `data.md` 내부 기준이다. 우리 판정선
   (`FRAME_BUDGET.md` §1 / `lib/targets.py`)은 **프레임 단위**이고 단계별 배정치는 폐기됐다.
   그러므로 이 "초과"는 **팀 합의된 선에 대한 판정이 아니다.**
2. **위 값은 하한이다.** 진짜 값은 더 크다.
3. **상류 후보는 `D1A1+bf+ts`다.** `ts`는 `INTERFACES.md` §B-4가 `☐`라 임의로 넣지 않았다 —
   **후보 전체는 이번에도 못 쟀다.**
4. **레버를 하나도 안 당겼다.** 분리형 근사(bilateral은 분리 불가라 알고리즘 변경이다) ·
   다운샘플 · sRGB 텍스처 포맷 · mediump · `d` 축소가 전부 미적용이다(`BF_LEVERS_NOT_PULLED`).

### 이식 정확성은 말할 수 없다

`INTERFACES.md` **§B-6 골든 이미지가 없다.** 이 결과는 **비용만** 말한다.
그리고 `cv2.bilateralFilter`의 내부 정의(채널 L1 합의 형태, 0..255 스케일, 원형 이웃,
`radius=d/2`)는 **OpenCV 구현을 읽어 옮긴 추론이고 상류 코드 인용이 아니다**(`BF_DEVIATION`).
경계 처리도 다르다 — OpenCV 기본은 `BORDER_REFLECT_101`, 이 이식은 `CLAMP_TO_EDGE`.

## 3. ④ 오버레이 — I칸 최초 실측

최초 범위 B·D·I 중 **유일한 미완이었다.** 상류 `scripts/emphasize.py` 명세대로 이식했다:
이중 스트로크(검정 밑선 + 대비색 본선) · 비채움 · `stairs` 노랑 / `person` 시안 ·
빨강 금지 · 깜빡임 금지 · 두께는 짧은 변 비례 720p 기준 4px · GL 드로우콜 1회.

| | 값 |
|---|---|
| I칸 (`gpu_sum` 차분, **박스 4개**) | **+0.562ms** |
| `stage_i_ms` 열 자체 (박스 4개) | 0.525ms |
| 개당 기울기 | 0.0044 (`gpu_sum` 차분) / 0.0020 (하위 열) ms/박스 |

**사실상 공짜다.** 🔴 **박스 개수 없는 I칸 숫자는 조건이 없는 숫자다** — 인용할 때 반드시
함께 옮긴다. 개당 기울기는 두 추정이 2배 어긋나고 32박스 런은 3분 봉투 점이라 지속 판정이 아니다.

**⚠ 선언되지 않았던 이탈 하나를 선언했다.** 스펙 문구는 *"비채움 — 경계선 밖은 일절 안 건드림"*
인데 이 구현은 스트로크를 경계선 **가운데 맞춤**해서 720p에서 경계 밖 **3px**을 덮는다.
`cv2.rectangle(thickness=t)`의 실제 동작과는 일치하므로 **이 구현이 오히려 상류와 맞을 가능성이
높지만**, §B-6 골든 이미지가 없어 확인할 수 없다(`HIGHLIGHT_DEVIATION`).
그리고 두 해석은 **비용도 다르다** — 가운데 맞춤이 띠마다 `4t²`을 더 채워 이 격자에서 약 4%다.

## 4. 관측한 것 · 못 한 것

### ⚠️ 런 안 GPU 드리프트를 처음 봤다 — 원인 미확정

`s6_1q` `#6`(`chain_bf_1q`)에서 **+360초부터 단조 상승**해 GPU 시간이 **24.157 → 27.301ms
(+13%)** 로 올랐다. 같은 런에서:

| | 시작 | 끝 | 판정 |
|---|---|---|---|
| GPU 시간 | 24.157 | 27.301 | 🔴 +13% |
| `render_latency` | 3.717 | 3.661 | 안 움직임 |
| 출력 간격 | 32.905 | 33.006 | 안 움직임 |
| `capture_to_render` | 76.414 | 76.660 | 안 움직임 |

**GPU 시간에만 나타난다.** 발열/DVFS가 후보지만 **이 세션은 기기 온도를 기록하지 않았다.**
그리고 `s5_bf`의 같은 무게 런 6개는 5등분에서 평평했다(폭 0.027~0.268, 단조 램프 아님).
**원인을 특정하지 못했다** — 다음 세션에 기기 온도를 함께 기록해야 한다.

이 저장소는 지금까지 "발열 드리프트 없음"으로 기록해 왔다. 그 결론은 **이만큼 무거운 arm이
없었기 때문**일 수 있다.

**"드리프트 이전 값"을 소수 셋째 자리로 인용하지 말 것.** `#6`의 평평 구간 자체가 60초
버킷마다 24.106~24.280으로 흔들리고(폭 0.3ms) 그 안에 23.973 버킷도 있어서, 컷을
`t<300s`로 잡으면 24.193 / `t<360s`로 잡으면 24.155가 나온다 — **컷 선택이 만드는 차이보다
구간 내 흔들림이 크다.** 그래서 이 보고서는 **같은 arm의 3분 반복 런 두 개가 정확히
일치하는 값(24.109, `#1`·`#2`)** 을 미드리프트 기준으로 쓴다. 그 둘은 전부 평평 구간이고
서로 p50 차이가 0.000이다(다만 3분 봉투 점이다).

그러므로 **중복 계상량은 `+18.960`(전체 창) ~ `+19.719`(미드리프트 기준) 범위**다.

### 안전 회귀 — `evaluated: false`

**③ 탐지가 미구현이라 위험물 강조 회귀를 측정할 수 없다.** 성능만 있는 보고는 불완전한 보고다.
④ 오버레이를 그렸다는 것이 "위험물을 놓치지 않았다"가 아니다 — 정적 더미 박스다.
깜빡임이 없는 것도 성능 근거가 아니다(정적이라 구조적으로 없다. 실제 깜빡임 위험은
H칸 = ③ N프레임 주기이고 미구현이다).

### 프레임타임·지연은 여전히 안 움직인다

21런 전부 프레임타임 p50 32.7~32.9 / p95 38.0~38.5, `capture_to_render` p50 76.3~77.3이다.
**40ms의 GPU 작업을 얹어도 안 움직인다** — 프레임타임은 카메라 공급에 묶인 바닥값이고,
지연은 빈 파이프라인에서 이미 예산을 넘고 있다. **지연 조사는 여전히 프로젝트 최대 위험이다.**

## 6. 인용 규칙 (이 보고서에서 숫자를 옮길 때)

1. **열 이름과 계측 방식을 함께 옮긴다.** `gpu_sum_ms`(패스별) / `gpu_frame_ms`(단일 query)는
   다른 물리량이고 **서로 빼거나 더하지 않는다.**
2. **분모도 같은 계측의 것으로만 뺀다** — 패스별 arm은 `blit_2pass`, 단일 arm은 `blit_2pass_1q`.
3. **D칸은 arm 간 차분이다.** `stage_d_total_ms`가 아니다. 조합 arm에는 하위 열 분해를 내지 않는다
   (하위 열이 한 패스 밀려 있고 융합은 패스 경계가 체인과 다르다).
4. **`stage_i_ms`에는 박스 개수를 붙인다.**
