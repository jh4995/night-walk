## 0. 결론 먼저

1. **구조** — 3스레드. 카메라 / 렌더(매 프레임) / **탐지(N프레임마다 비동기)**. 배분치와 무관하게 성립하는 결론이다. (§1-4)
2. **스택** — Android 네이티브(Kotlin) + CameraX + **ONNX Runtime Mobile** + OpenGL ES 3.1 셰이더. (§4)
3. **못 정하는 것** — 추론 가속(EP). **팀 데모 기기의 SoC가 정해져야** 답이 나온다. (§5)

이 문서가 팀에 처음 내놓는 것은 **§1 프레임 예산 체계**와 **§2 지연 예산**이다. 지금 팀에는 "빠르다/느리다"를 말할 공통 단위가 없다.

## 1. 프레임 예산 — 팀 공용 단위

### 1-1. 목표에서 유도되는 값

| 항목 | 값 | 성격 |
|---|---|---|
| 목표 해상도 | 1280×720 | 신청서 성능 목표 |
| 목표 처리율 | **15 FPS 이상** | 신청서 성능 목표 |
| **프레임당 예산** | **1000 / 15 = 66.7 ms** | 위 두 줄에서 **유도** |
| p95 프레임타임 관리선 | **< 80 ms** 🟡 | **제안.** 평균이 맞아도 tail이 튀면 보행자는 끊김을 느낀다 |
| 지속 성능 기준 | **연속 10분 후에도** 만족 🟡 | **제안.** 발열 스로틀링 반영 |

**헤드룸 규칙 🟡** — 기능에 배정 가능한 총량은 66.7ms의 **80%(≈53ms)까지**. 나머지 20%는 발열 드룹·GC·OS 스케줄링 지터용이며 기능에 배정하지 않는다.

> 이 표에 추정치는 없다. 66.7은 목표에서 나눈 값이고, 80ms·10분·80%는 **제안하는 기준**이다.

### 1-2. 용어를 먼저 고정한다

- **프레임타임** — 파이프라인이 프레임 1장을 뱉는 주기(= 1/FPS). 목표 ≤ 66.7ms
- **단계 시간** — 아래 표 A~J 각 구간이 쓰는 시간. **단계 오너가 자기 칸을 실측으로 채운다**
- **글래스-투-글래스 지연** — 세상의 사건이 화면에 뜰 때까지. **프레임타임과 다른 숫자다** (§2)

### 1-4. 탐지는 왜 비동기여야 하나 — 배분치와 무관한 결론

탐지(YOLO 추론)는 파이프라인에서 **단일 최대 비용 단계**다. 그래서 매 프레임이 아니라 N프레임마다 돈다 — 여기까지는 팀이 이미 같은 방향이다(임베디드 담당 조사 §16도 YOLO만 5~15fps로 따로 뺐다).

문제는 그 다음이다. **N프레임마다 돌리면 그 프레임만 무거워진다.** 가벼운 프레임 여러 장과 무거운 프레임 한 장이 번갈아 나오면:

- 평균 프레임타임은 목표를 통과할 수 있다
- 그러나 **p95는 그 무거운 프레임에 걸린다** — 걷는 사람은 주기적인 끊김으로 체감한다

그래서 탐지를 **별도 스레드로 빼고**, 렌더 경로는 "가장 최근에 완료된 탐지 결과"를 쓴다. 그 사이 프레임은 트래킹이 박스를 이어받는다.

> **이 결론은 각 단계에 몇 ms가 배정되든 성립한다.** 실측 전에 미리 확정할 수 있는 유일한 구조 항목이다.
> 그리고 **"평균 15FPS"만 목표로 두면 이 문제가 안 보인다.** p95를 목표에 넣자는 제안(§1-1)의 근거가 이것이다.

## 2. 지연 예산 — 프레임타임과 다른 숫자다

**⚠️ 프레임타임을 목표에 맞춰도 지연은 그 값이 아니다.**

카메라 노출·ISP 큐 + 파이프라인 + 디스플레이 합성이 **직렬로 쌓이므로**, 실제 지연은 프레임타임보다 크다. 탐지 비동기화(§1-4)는 여기에 1~2프레임을 **더** 얹는다. **얼마나 큰지는 미측정이다.**

### 글라스 A 구조와 합산할 때

팀장 스마트글라스 보고서의 GO/NO-GO 게이트는 **왕복지연 < 200ms**다. 짚어둘 것 하나 — **이 200ms는 파이프라인 지연을 대체하는 게 아니라 더해진다.**

```
글라스 카메라 → Wi-Fi 왕복 → 폰 파이프라인 → 글라스 OSD
                (200ms 게이트)    (미측정)
```

즉 사용자가 체감하는 지연은 `200ms + 파이프라인 지연`이다. **왕복 게이트를 통과해도 최종 지연이 보행 안전에 허용되는지는 별도 판정이 필요하다.**

> **A'(폰 촬영·추론 → 글라스는 표시 전용)는 Wi-Fi가 프레임 경로에 없다.** 결과 JSON만 내려보내므로 이 합산이 발생하지 않는다.
> → 팀장이 A'를 1차 완성 목표로 둔 판단은 **지연 관점에서도 옳다.** §10 질문 2로 상신한다.

## 3. 런타임 파이프라인 — 프레임 1장이 지나가는 길

```
                    ┌─────────────────── 카메라 스레드 ───────────────────┐
  [센서]  →  ① 취득  →  ② 포맷/색공간
                    └──────────────┬───────────────────────────────────┘
                                   │  (프레임 핸들 = GPU 텍스처)
              ┌────────────────────┼─────────────────────────────┐
              ▼                    │                              ▼
  ┌──── 렌더 스레드 (매 프레임) ────┐ │          ┌──── 탐지 스레드 (N프레임마다, 비동기) ────┐
  │ ③ 글레어 억제  (GPU 셰이더)     │ │          │ ⑥ 전처리(letterbox·정규화)              │
  │ ④ 저조도 개선  (GPU 셰이더)     │ │          │ ⑦ YOLO 추론  (ORT Mobile + EP)          │
  │ ⑤ 트래킹 보간  (최근 박스 유지) │◄┼──게시────│ ⑧ 후처리(decode·NMS)                    │
  │ ⑨ 선택적 강조  (오버레이 렌더)  │ │  (최근    └─────────────────────────────────────────┘
  │ ⑩ 디스플레이 합성              │ │   결과)
  └────────────────────────────────┘ │
              │                       │
              ▼                       │
          [출력] ◄────────────────────┘
```

- 렌더 경로는 **탐지 완료를 기다리지 않고** 항상 "가장 최근에 완료된 탐지 결과"를 쓴다.
- **트래킹은 IoU 매칭 + 짧은 TTL** 🟡 — KLT 옵티컬플로우는 **고정 카메라 전제**라 들고 걷는 폰의 큰 전역 모션에서 가정이 깨진다. AID와 밤마실이 갈리는 지점.
- **⑨ 강조는 "탐지 박스 내부에서만 엣지 추출"** 🟡 — 임베디드 담당 조사 §9.2 채택. 전체화면 Canny는 저조도 노이즈까지 엣지로 잡아 배경이 폭발한다. 킥오프의 *"세그멘테이션 말고 대형물 + 엣지·경계"* 컨셉과도 맞는다.
- **대가:** 강조 오버레이가 실제 장면보다 **1~2프레임 늦는다.** §10 질문 4.

**A(Android 네이티브)를 고르는 이유** — 병목이 카메라 프레임 취득 · GPU 셰이더 · 온디바이스 추론 세 곳인데, 크로스플랫폼은 이 셋을 전부 네이티브 채널로 뚫어야 해서 "크로스"의 이점이 사라지고 복잡도만 남는다.

### Unity 기반 대안에 대해 *(공유본에서는 뺀 절)*

임베디드 담당 조사는 **Unity + Cardboard XR Plugin + Unity Inference Engine**을 권장한다. 그 조사는 카드보드를 최종 출력 장치로 전제했는데, 그 사이 팀장이 **Rokid Glasses**로 출력 장치를 확정했고 근거에 이렇게 적혀 있다:

> *"표준 Android(12) 기반 → 기존 폰 앱 코드·ONNX 추론 스택 그대로 재사용. 버려지는 자산 0"* — 팀장 보고서 §2

**이 이점은 Android 네이티브일 때 성립한다.** 덧붙여 Unity Inference Engine은 자체 백엔드(CPU/GPU Compute)만 제공하고 **NNAPI·QNN 같은 벤더 NPU EP를 노출하지 않는다.** 킥오프의 *"최신 폰 NPU를 쓰자"*가 Unity에서는 막힌다. 임베디드 담당 조사도 §8.2에서 2차 최적화 시 NCNN 네이티브 플러그인으로 내려가라고 적었는데, 그건 Unity의 이점을 반납하고 JNI 복잡도를 얹는 경로다.

> 다만 이 판단은 **"카드보드/글라스 UI를 우리가 직접 그리느냐"**에 달려 있다. Google Cardboard SDK는 Unity 외에 Android 네이티브(NDK) 버전도 제공하는 것으로 파악되나 **최신 유지보수 상태는 미확인**이다.

## 5. 온디바이스 실현 — 추론 가속(EP) 🔴

**팀장 선행 프로젝트(AID)는 NVIDIA GPU + TensorRT 기반인데, 폰에는 NVIDIA GPU가 없다.** 폰에서 ONNX를 가속하는 경로는 셋이고, **SoC마다 최적이 다르며 드라이버 품질 편차가 크다.**

| 순위 | EP | 성격 | 실측 관전 포인트 |
|---|---|---|---|
| 1 | **XNNPACK (CPU)** | 어디서나 동작, 안정 | **베이스라인.** 여기서 바닥을 찍고 시작 |
| 2 | **NNAPI** | HW 추상화 (GPU/DSP/NPU) | static shape 필수. 드라이버가 서브그래프를 CPU로 떨구지 않는지 |
| 3 | **QNN (Qualcomm)** | Snapdragon NPU/HTP 직접 | Snapdragon 한정. 최고속 가능성, 기기 종속 |

**결정 = "이 순서대로 실측한다"는 것 자체다.** 측정 없이 EP를 고르면 근거가 없다.

> 킥오프의 *"최신 폰 NPU를 쓰면 된다"*는 방향은 맞지만, **NNAPI/QNN이 실제로 NPU를 잡는지는 기기별로 갈린다.** §9 요청 1번이 최우선 후속이다.

## 6. 입력·출력 경로 추상화 🟡

킥오프 이후 **입력도 출력도 여러 갈래가 됐다.** 지금 구조에 넣어두지 않으면 나중에 파이프라인을 다 뜯게 된다.

```
[폰 카메라 (라이브)]  ─┐                              ┌─▶ [폰 화면]        ← 구조 B
[영상 파일 (녹화)]    ─┼─▶ 공통 프레임 소스 ─▶ 파이프라인 ─┼─▶ [글라스 OSD]     ← 구조 A'
[화면 캡처 (게임)]    ─┤                              └─▶ [카드보드 좌우눈]
[글라스 카메라 + Wi-Fi]─┘  ← 구조 A (지연 합산 §2)
```

| 얻는 것 | 설명 |
|---|---|
| **팀장 3단 보험(A/A'/B)을 코드 한 벌로 흡수** | A'→A 전환이 입출력 어댑터 교체로 끝난다 |
| **발표장 보험** | 라이브 야간 시연이 불가능할 때 녹화·게임화면으로 즉시 전환 |
| **재현 가능한 회귀 테스트** | 같은 영상 = 같은 입력 → 성능·안전 회귀를 숫자로 비교 |

> ⚠️ 녹화 경로를 쓰려면 **촬영 규약**이 대량 촬영 **전에** 확정돼야 한다. → §9 요청 3.

## 7. ② 저조도 개선의 처리 방식은 "런타임 구조 결정"이다 🔴 *(공유본에서는 뺀 절)*

모델링 담당 `data.md`가 ② 처리 방식을 **A/B/C 3후보 미결**로 두고 FPS 실측 후 판정하기로 했다. 모델 선택처럼 보이지만 **실제로는 파이프라인 구조가 갈리는 결정**이다.

| 후보 | 내용 | 런타임에 미치는 영향 |
|---|---|---|
| **A. 고정 휴리스틱** | CLAHE + 감마 + 노이즈 억제 | GPU 셰이더 1패스. **추론 1개(탐지)** — §3 구조 그대로 |
| **B. 초경량 커브추정** | Zero-DCE / SCI 계열 | 작은 CNN이 **매 프레임** → **추론 2개.** 스레드 배치·메모리·EP 공유 재설계 |
| **C. dense 복원망** | LoLI-Street 33k쌍 본학습 | 큰 CNN이 **매 프레임** → **추론 2개 + 예산 붕괴 위험** |

**§3의 3스레드 설계는 탐지 추론 1개만 가정한다.** B/C면 매 프레임 enhancement 추론이 하나 더 붙어 구조가 달라진다.

**제안**
1. **A를 GPU 셰이더로 먼저 구현해 기준선을 만든다.** 학습이 필요 없어 즉시 착수 가능하고, B·C의 비용을 비교할 대상이 생긴다.
2. **A/B/C의 폰 위 비용은 내가 측정한다.** PC에서 잰 숫자는 폰 숫자가 아니다.
3. 모델링 담당이 설계한 **`무처리`/A/B/C 4-arm 비교**는 그대로 유효하다 — 단 §10 질문 1이 먼저 풀려야 판정 기준이 정해진다.

> 📌 `data.md`는 **② 단독 ≤20ms** 게이트를 두고 그 근거로 `hardware_inference.md` §5를 인용하는데, 나는 원문을 열람하지 못했다. 내가 D칸을 비워뒀으므로 **숫자 충돌은 없다.** 다만 그 20ms가 PC 기준인지 폰 기준인지는 확인이 필요하다.

```
모델 export 규약 ☐ ──┬──▶ D(ORT) 🟡 ──▶ E(EP 실측) 🔴
                    └──▶ F(포맷) 🟡
①② 모듈 시그니처 ☐ ────▶ G(GLES) 🟡 ──▶ H(버퍼경로) 🟡 ──▶ I(GL렌더) 🟡
플랫폼 확정 ───────────▶ A(Android) 🟡 ──▶ C(CameraX) 🟡 ──▶ K(동시성) 🟡
② 방식 A/B/C 판정 🔴 ──▶ 스레드 구조 확정
```

| 지금 병렬로 되는 것 | 막힌 것 (선행 필요) |
|---|---|
| A·B·C·K — 플랫폼·빌드·카메라·동시성 골격 | **E (EP)** ← 기기 기종 + 탐지 입력 해상도 |

| **빈 파이프라인 PoC** → 분해표 A·B·I·J 칸 | **스레드 구조** ← ② 방식 A/B/C 판정 |
| **② A안(고정 휴리스틱) 셰이더 구현** | **트래킹 TTL** ← 탐지 주기 N 실측 |

> **다음 산출물은 빈 파이프라인 PoC다.** 아무 처리 없는 상태의 프레임타임 = **§1-3 표 전체의 분모.**

| 3 | 촬영하는 모든 사람 | **야간모드/HDR OFF · CFR 30fps · 회전 메타 0°** | §6 녹화 경로 + 회귀 테스트 자산 |
| 4 | 팀장 | ①②가 **픽셀 병렬화 가능한 형태인가** | G·H·I 세 결정이 잠겨 있음 |

**요청 2 — 학습 export 전에 필요한 3줄**

1. **입력 shape 완전 static** (동적 축 금지) — 동적이면 NNAPI/GPU EP가 서브그래프를 못 잡고 통째로 CPU로 떨어진다
2. **NMS 미내장 raw 출력** — 모바일 EP 대부분이 `NonMaxSuppression` 미지원이라 그래프가 쪼개지고 텐서가 GPU↔CPU를 왕복한다. 또 conf/IoU 임계값은 야간 실기기에서 조정해야 하는데, 내장되면 매번 재export다
3. **opset 13** — 너무 높으면 모바일 EP 미지원 연산자 발생

> 상세 규약은 별도 문서로 배포. 한 가지만 미리: **인수 판정용 골든 샘플을 LoLI-Street 동봉 라벨로 만들면 안 된다.** `data.md`가 지적한 대로 pseudo-label 가능성이 있어 판정 기준으로 쓸 수 없다.

## 10. 미결 질문 *(대부분 공유본에서 뺌 — 7/29 사전미팅용)*

**1. ①②의 결과를 사용자가 어디서 보는가?** ⭐ 가장 먼저 답이 필요하다

팀장 보고서 §3-1이 지적한 대로 **시스루 광학은 빛을 더할 수만 있고 뺄 수 없어 눈부심 억제가 원리적으로 불가능**하다. 그래서 UX가 아이콘 + 방향 화살표 + 오디오 우선으로 정리됐다.

그 귀결이 아직 문서화되지 않았다: **글라스가 최종 출력이면 ①눈부심 억제·②저조도 개선의 결과 영상을 사용자가 볼 수 없다.** ①②는 탐지 전처리로만 남고, 심사에서 4단계 중 2단계가 화면에 안 나타난다.

파급:
- 모델링 담당의 **표시용/탐지용 경로 분리(H3)**가 무의미해진다 — 표시 경로 자체가 없으므로
- `data.md`의 ② A/B/C 판정 기준이 바뀐다. "사람 눈에 좋은가"가 빠지고 **탐지 mAP만** 남는다
- §1-3의 C·D 칸의 목적이 달라진다

**→ 제안:** 팀장이 최후 폴백으로 둔 **B(폰 화면)를 폴백이 아니라 "①② 시연 경로"로 재정의**하자. 데모에서 폰 화면과 글라스를 **동시에** 보여주면 4단계가 전부 보인다. 폰 화면이 ①②의 개선 결과를, 글라스가 ③④의 위험 강조를 담당한다.

**2. 구조 A의 지연 총합을 허용하는가?** (§2)
Wi-Fi 왕복 200ms에 파이프라인 지연이 더해진다. A'는 이 문제가 없으므로, A는 "글라스 카메라를 쓰는 것"이 시연상 얼마나 중요한지와 맞바꾸는 결정이다.

**3. 성능 목표를 "평균 15FPS + p95 < 80ms"로 갱신하는 데 합의하나?**
킥오프의 *"15fps는 장시간이면 UX 낙제"* 지적과 같은 문제다. 평균만 보면 안 보인다(§1-4).

**4. 강조 오버레이가 1~2프레임 늦는 것을 허용하나?**
허용 못 하면 §3의 비동기 설계가 바뀐다.

**5. 지속 성능 기준을 "연속 10분 후에도 만족"으로 두는 데 합의하나?**
