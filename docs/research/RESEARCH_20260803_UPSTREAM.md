> 병렬로 돌릴 수 있고, ②의 속도 게이트가 ③의 지연에 더해지지 않는다."**

### 🔴 이것이 내 버짓표의 직렬 전제를 깬다

`FRAME_BUDGET.md` §3 본표는 A~J를 **한 줄로 더하는** 구조다. 분리가 확정되면:

```
지금 전제 (직렬):   A → B → C → D → E → F → G → H → I → J   (전부 합산)

분리 후 (병렬):     A → B ─┬─ D(②) ────────────┬─ I(④) → J
                           └─ E·F·G(③, N프레임마다) ─┘
                           ↑ 두 갈래가 동시에 돈다 = max(D, EFG) 이지 D+EFG 가 아니다
```

⚠️ **아직 고치지 않았다.** 팀 추인 대기이고, GPU/CPU 자원을 실제로 나눠 쓸 수 있는지는
**내가 실기기에서 재봐야 안다** — 같은 GPU를 두 경로가 쓰면 병렬이 공짜가 아니다.
버짓표에는 **주석으로만** 반영했다.

⚠️ 저쪽도 대안 (b)를 닫지 않았다 — *"② 적용본으로 ③를 재학습하면 도메인 불일치가 사라져
결과가 뒤집힐 수 있다"*. 다만 arm을 바꿀 때마다 재학습이라 비용이 크다.
⚠️ **대시캠 한계는 그대로** — 보행 시점(`C5`)에서 재확인해야 한다.

## 6. ② 후보가 **조합**으로 넘어갔고, 해상도가 품질을 바꾼다

- **잠정 1위 `D1A1+bf`** (Drago → CLAHE → bilateral). 단일 arm은 3축(글레어·대비·노이즈)에서 전멸.
  채택되면 **①글레어 억제가 ②에 흡수된다** — 내 버짓표 §3 주4와 같은 이야기다.
- 🔴 **글레어 지표가 처리 해상도에 크게 의존한다** — 같은 사진에서 D1의 광원 코어가
  원본 **10** / 720p **151** / 640 **158** / 480 **161**. Drago의 전역 로그 매핑이 입력 전체
  통계로 정해지기 때문이다. **"해상도를 낮춘다"는 속도만의 문제가 아니라 표시 품질 자체를 바꾼다.**
- `C6` 결론: **속도 게이트와 3축을 확실히 동시에 만족하는 조합이 없다.**
  CPU 기준 `D1A1+bf` = 720p **101.2ms** / 854×480 65.6ms / 640×360 33.1ms.
- **② 는 고전으로 간다 — 결정 (8/1, 🗣️ 팀 회의 추인 대기).** 근거는 성능이 아니라 **데이터**:
  보유한 유일한 대규모 paired 데이터의 포화 광원이 **0.00%** 라 딥러닝 ②는 글레어 축을
  학습할 방법이 없다.

### 🔴 여기서 내가 상류 결론을 뒤집을 수 있다

```
상류 C6:   "속도 게이트와 3축을 동시에 만족하는 조합은 없다"   ← CPU 측정
            D1A1+bf 720p = 101.2ms
내 GPU:     D1 단독 6.280ms · A1 단독 7.176ms  (A34, 지속 런)
```

⚠️ **조합은 미측정이다.**

> 🔴 **정정 (2026-08-03, 코드 대조) — 두 arm은 색공간 변환을 공유하지 않는다.**
>
> 이 문단은 원래 *"두 arm이 LAB 변환을 공유하므로 한 번만 하면 단순 합(13.5ms)보다 싸진다"* 고
> 적었다. **코드와 어긋난다.** `android/.../gl/DragoStage.kt`는 `LabGlsl`을 **한 번도 쓰지 않는다** —
> 선형화는 `pow(rgb, 2.2)`, 휘도는 `dot(lin, vec3(0.299,0.587,0.114))`로 **선형 RGB 3채널 전부**에서
> 돌고(그 파일이 *"A1·A2가 LAB의 L만 건드리는 것과 다르다"* 고 직접 적고 있다), LAB의 `L`에서
> 도는 것은 **A1·A2**다.
>
> 74%라는 수치의 출처인 `FRAME_BUDGET.md` §3 주3도 **"A1·A2가 공유하는 LAB 변환"** 이라고
> 정확히 적었는데, 여기로 옮겨 적으면서 그 쌍이 **D1·A1로 바뀌었다.** 그리고 두 선형화 곡선이
> 서로 다르다 — `LabGlsl`은 sRGB piecewise(지수 2.4), Drago는 순수 `pow(x, 2.2)`라 하나로 접을
> "공통 선형화"가 애초에 없다.
>
> ⇒ **D1→A1을 그대로 이어붙여도 LAB 변환은 한 번뿐이다.** 이 문서를 근거로 착수한 작업이
> 있다면 그 전제부터 다시 잡아야 한다.

**그러면 조합의 비용 우위는 어디서 오나 — 이것이 측정 대상이고, 주장이 아니다.**

| | 항목 |
|---|---|
| ✅ 아낄 수 있다 | 전체화면 적용 패스 1개와 그 **중간 RGBA8 쓰기·읽기**, 두 스테이지 사이의 sRGB 인코드/디코드 왕복 |
| ❌ 못 아낀다 | **CLAHE의 정방향 LAB은 픽셀당 2회가 구조적으로 불가피**하다 — 히스토그램(컴퓨트)과 적용(프래그먼트)이 별개 패스이고, GL은 중간 텍스처 없이 픽셀 값을 다음 패스로 못 넘긴다 |
| ❌ 못 아낀다 | 전체화면 **통계 스캔 2회** — Drago 계수는 화면 전체 통계에서 나오고 CLAHE 히스토그램은 그 **적용 결과**를 먹는다. 의존이 직렬이다 |
| ⚠ 교환이다 | 융합(중간 materialize 제거)은 위 절감을 **Drago 톤맵을 픽셀당 2회 평가하는 것**과 맞바꾼다. 어느 쪽이 이기는지는 재봐야 안다 |

즉 검증 가능한 불변식은 "LAB 1회"가 아니라 **전체화면 적용 패스 1개 / 픽셀당 색공간 왕복 1회 /
중간 RGBA8 materialize 0회**다.

**GPU에서 720p 조합이 게이트 안이면** 해상도를 640×360으로 깎을 이유가 사라지고,
§6의 "해상도를 낮추면 글레어 품질이 바뀐다"는 문제도 같이 없어진다.

🚫 **여기에 기대값을 적지 않는다.** 단순 합 13.5ms는 **추정이지 예측이 아니고**, 측정 전에 숫자를
적으면 판정이 오염된다. 값이 큰 측정이라 우선순위만 여기로 올린다.
