## 2. 모델링 담당 레포가 실제로 한 것 (HEAD `60bc2a6`)

### 2-1. A안이 재설계됐다 — 5 톤커브 × bilateral

`docs/lowlight_classical_result.md:57-64` 기준. **모든 arm이 2단 직교 구조다:**

```
입력 → [ 톤커브 스테이지 ] → [ bilateral (선택) ] → 출력
         A1  A2  D1  R1  L1        = "+bf"
```

5개 톤커브 × bf 유무 2가지 = **10 arm + 대조군 `none`**. 구현은 `scripts/lowlight.py` 레지스트리.

**bilateral을 톤커브에서 떼어낸 이유가 설계의 핵심이다**(`lowlight_classical_result.md:144-150`):
원래 A안이 `CLAHE + 감마 + 노이즈 억제`로 **묶여** 있으면 A1과 A2를 비교할 때 톤커브 차이와
노이즈 처리 차이가 뒤섞여, 가설 H2("고전은 노이즈를 함께 증폭해 탐지를 해친다")를 arm 차이로
읽을 수 없다. 직교로 떼면 `X` vs `X+bf` 한 쌍으로 H2가 바로 판정된다.

### 2-2. 실제 파라미터 값 — §B-5를 채울 수 있는 값이 존재한다

`lowlight_classical_result.md:75-141`. **⚠️ 이건 팀장이 준 계약 답변이 아니라 모델링 담당의 탐색
구현값이다.** `INTERFACES.md` §B는 **팀장 → 팀원2** 계약이므로 `☐`는 여전히 `☐`다.
다만 §B-6이 요구한 **"PC 레퍼런스 구현"의 실체**로는 이것이 있다.

| arm | 구성 | 동작 채널 |
|---|---|---|
| `A1` | `CLAHE(clip_limit=2.0, tile=8, gamma=0.75)` | **LAB의 `L`** |
| `A2` | `AGCWD(alpha=0.5)` (Huang 2013) | **LAB의 `L`** |
| `D1` | `Tonemap Drago(gamma=2.2, saturation=1.0, bias=0.85)` | 선형 RGB |
| `R1` | `Tonemap Reinhard(gamma=2.2, intensity=0.0, light_adapt=0.8, color_adapt=0.0)` | 선형 RGB |
| `L1` | `LIME(radius=16, eps=1e-3, floor=0.15, gamma=0.8, scale=4)` — fast guided filter | RGB 비율 |
| `+bf` | `Bilateral(d=7, sigma_color=50, sigma_space=50)` | BGR |

> `d`를 키우면 급격히 비싸진다 — *"720p 실시간을 노리면 `d<=7`을 유지할 것"* (`:156`).

### 2-3. A안 서브암 A1/A2/A3 — 그리고 A3는 **temporal이다**

`lowlight_classical.md:142-146`:

| 서브암 | 구성 | 예상 비용(720p, CPU) |
|---|---|---|
| **A1** (기준선) | CLAHE(LAB L) + 감마 | ~7ms |
| **A2** | AGCWD + bilateral | ~16ms |
| **A3** | A1/A2 중 우세안 + **시간축 IIR 평활 + 모션적응 시간축 노이즈 억제** | +1ms 미만 |

**A3가 `INTERFACES.md` §B-4(프레임 간 상태)에 대한 사실상의 답이다.**
`lowlight_classical.md:98`: *"비용: 이전 프레임 1장 버퍼 + IIR 블렌딩(`out = α·cur + (1-α)·prev`) = 1ms 미만"*.
저쪽은 **temporal 상태를 쓰고 싶어 한다.** 근거는 (a) 프레임별 적응이 **플리커**를 유발하고
(b) 시간축 노이즈 억제가 단일프레임 기법이 못 얻는 SNR 이득을 준다는 것(`:19-22`의 결론 3).

> ⚠️ 계약서(`INTERFACES.md` §B-4)는 temporal이면 **리셋 조건·수렴 시간 정의**를 요구하고,
> 프레임 드롭과의 상호작용으로 생기는 화면 번쩍임을 **안전 문제**로 규정한다. 아직 미정의다.

### 2-4. CPU 실측 숫자 (모델링 담당 측정 — 폰 숫자가 아니다)

측정 조건: 학습 PC CPU, `opencv-python 5.0.0` + NumPy float32, LOL 이미지 리사이즈,
warm-up 2회 후 **10회 median** (`lowlight_classical.md:48`).

| arm | 720p | 854×480 | 640×360 | 20ms 게이트 |
|---|---|---|---|---|
| A1 (CLAHE+감마) | **5.3ms** | — | — | ✅ |
| A2 (AGCWD) | **6.2ms** | 3.0ms | 1.4ms | ✅ |
| A1+bf | **17.6ms** | 9.3ms | 5.4ms | ✅ |
| D1 (Drago) | 82.9ms | 37.3ms | **15.7ms** | ❌ (640×360만 ✅) |
| R1 (Reinhard) | 92.7ms | 39.2ms | 18.9ms | ❌ |
| L1 (LIME) | 83.8ms | 36.6ms | 20.1ms | ❌ |

**세 가지 결론이 여기서 나온다:**

1. **`lowlight_classical.md:179` — "② 단독으로는 병목이 아니다."**
   A1·A2가 5~6ms, bilateral을 얹어도 17ms. 같은 레포의
   `hardware_inference.md` §2 *"② 저조도 개선 — 실질 병목 ⚠️"* 서술은 **C안(dense 복원망)에만
   해당**한다는 것이 실측으로 확인됐다.
2. **`:20` — Retinex·톤매핑 계열은 20ms 게이트에서 전멸했으나 기각이 아니라 보류.**
   *"이는 CPU·NumPy 구현 기준이고, 연산 구조상 **GPU 셰이더 이식 시 순위가 뒤집힐 수 있어**"*
   (`:148`도 같은 취지: *"셰이더 이식 또는 480p 내부 처리 시 재평가 대상"*).
   → **셰이더 이식이 내 일이다. 순위를 뒤집을 수 있는지가 열린 질문이다.**
3. **해상도 하향이 후보군 자체를 넓히는 결정이다**(`:75`). 480p로 내리면 톤매핑 계열이 게이트 안에 들어온다.

### 2-5. 🔴 가장 중요 — A1·A2는 **구조적으로 눈부심을 못 누른다**

`lowlight_classical_result.md:160-178`:

| arm | 적응 범위 | 하이라이트 거동 |
|---|---|---|
| `A1` | 타일(국소) | ❌ 못 누름 (포화 소폭 감소) |
| `A2` | 전역 | ❌ 못 누름 (**포화 15배 확대**) |
| `D1` | 전역 로그 압축 | ✅ **실제 억제** (상위 1% 밝기 −81, 포화 0.67%→0.04%) |
| `R1` | 국소 적응 | △ 포화만 억제 |
| `L1` | 공간적(조도맵) | ❌ 증폭 안 함 (억제도 아님) |

> *"대상 사용자가 **광과민** 야맹증이라 눈부심 억제가 목적 축인데, `A1`·`A2`의 톤커브는
> **단조 증가**라 어떤 입력값도 낮출 수 없다. 튜닝으로 해결되는 문제가 아니라 **구조적 한계**"*

그래서 저쪽 결론(`lowlight_classical.md` 6-3-6)은 **"어느 arm도 단독으로는 목적을 충족하지
못한다"** 이고, 다음 실험은 단일 arm이 아니라 **조합 `D1(글레어 압축) → A1(국소 대비) → bf(노이즈)`** 다.

**이것이 ①과 ②의 경계를 바꾼다.** `lowlight_classical.md:22`(결론 4):
*"local tone mapping 계열은 강광원 억제와 암부 증폭을 **한 연산**으로 하므로, ①글레어 억제를
별도 단계로 두지 않아도 될 가능성이 있다 → 파이프라인 단순화 + FPS 예산 확보."*
→ `FRAME_BUDGET.md`의 **C칸과 D칸이 하나로 합쳐질 수 있다.**

> **적용은 되는데 표시가 안 된다.** 포팅 시 이 값들을 코드에서 직접 읽어야 한다.

## 3. 내 S3(② 셰이더) 계획에 대한 귀결

원문을 읽기 전 세운 계획이 **네 곳에서 틀렸다.**

| 내 가정 | 원문 | 조치 |
|---|---|---|
| CLAHE를 **YUV의 Y**에 적용 (`INTERFACES.md` §B-2 제안값) | 저쪽은 **LAB의 `L`** (`A1`·`A2` 둘 다) | **LAB L ≠ YUV Y.** 포팅 결과가 골든 이미지와 어긋날 지점. §B-2를 다시 물어야 한다 |
| 타일 격자 8/16/32 **스윕**해서 봉투 | `tile=8` **확정값이 구현에 있다** | 스윕은 봉투용으로 유지하되 **8을 기준점으로** 삼는다 |
| 노이즈 억제를 **구조 봉투 2점**으로 추정 | `Bilateral(d=7, σc=50, σs=50)` **실제 값 존재** | 추정 대신 **그 값으로 포팅** |
| ②를 **stateless**로 구현 | **A3가 temporal IIR** | stateless는 A1/A2까지만. **A3는 §B-4 답변 없이는 못 짓는다** |

**그리고 재야 할 대상이 늘었다.** 원래 "A안 = CLAHE+감마" 하나였는데:

1. **A1 · A2 · A1+bf · A2+bf** — 저쪽 CPU 숫자가 있으니 **GPU 대비표**를 만들 수 있다
2. **D1 · R1 · L1** — CPU에서 게이트 4배 초과지만 **셰이더에서 순위가 뒤집히는지가 열린 질문**이고,
   `D1`은 **글레어를 실제로 누르는 유일한 후보**라 값이 가장 크다
3. **A3(temporal IIR)** — §B-4 답변 대기

**우선순위 판단:** 2번이 가장 값지다. 1번은 저쪽 CPU 숫자가 이미 "게이트 통과"라 GPU에서도
통과할 가능성이 높아 **판정을 바꾸지 않는다.** 반면 2번은 *"어느 arm도 단독으로는 목적을 충족하지
못한다"* 는 교착을 풀 수 있는 유일한 경로다 — GPU에서 D1이 게이트 안에 들어오면
**①②를 한 연산으로 합치는 길이 열린다.**
