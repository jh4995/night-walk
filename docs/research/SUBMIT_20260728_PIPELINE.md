> **작성:** 파이프라인 담당 · **제출:** 2026-07-28
> **대상:** 팀장 요청 리서치 **항목 ③ 파이프라인 연결** 전체 + **항목 ① 엣지 단위 붙이기** 중 런타임 부분

## 0. 결론 3줄

1. **구조** — 3스레드로 나눈다. 카메라 / 렌더(매 프레임) / **탐지(N프레임마다 비동기)**. 탐지가 단일 최대 비용 단계라 N프레임마다 돌 수밖에 없는데, 그러면 **그 프레임만 무거워져 프레임타임이 주기적으로 튄다.** 이 결론은 각 단계에 몇 ms가 배정되든 성립한다. → §1
2. **스택** — Android 네이티브(Kotlin) + CameraX + **ONNX Runtime Mobile** + OpenGL ES 3.1 셰이더. → §3
3. **못 정하는 것** — 추론 가속(EP) 하나. **팀 데모 기기의 SoC가 정해져야** 답이 나온다. → §6 요청 1번

## 1. 프레임 예산 — 팀 공용 단위

지금 팀에는 "빠르다 / 느리다"를 말할 공통 단위가 없다. 먼저 이걸 만든다.

### 1-1. 목표에서 유도되는 값

| 항목 | 값 | 성격 |
|---|---|---|
| 목표 해상도 | 1280×720 | 신청서 성능 목표 |
| 목표 처리율 | **15 FPS 이상** | 신청서 성능 목표 |
| **프레임당 예산** | **1000 / 15 = 66.7 ms** | 위 두 줄에서 **유도** |
| p95 프레임타임 관리선 | **< 80 ms** 🟡 | **제안.** 평균이 맞아도 tail이 튀면 보행자는 끊김을 느낀다 |
| 지속 성능 기준 | 위 값을 **연속 10분 후에도** 만족 🟡 | **제안.** 발열 스로틀링 반영 — 첫 30초 숫자는 데모 근거로 못 쓴다 |

**헤드룸 규칙 🟡** — 기능에 배정 가능한 총량은 66.7ms의 **80%(≈53ms)까지**로 잡는다. 나머지 20%는 발열 드룹·GC·OS 스케줄링 지터용이며 기능에 배정하지 않는다.

> 이 표에 추정치는 없다. 66.7은 목표에서 나눈 값이고, 80ms·10분·80%는 **제안하는 기준**이다.

### 1-2. 용어를 먼저 고정한다

"몇 ms 나와요?"는 항상 이 셋 중 하나를 지목해야 한다. 섞이면 대화가 헛돈다.

- **프레임타임** — 파이프라인이 프레임 1장을 뱉는 주기(= 1/FPS). 목표 ≤ 66.7ms
- **단계 시간** — 아래 표 A~J 각 구간이 쓰는 시간. **단계 오너가 자기 칸을 실측으로 채운다**
- **글래스-투-글래스 지연** — 세상의 사건이 화면에 뜰 때까지. **프레임타임과 다른 숫자다**

### 1-3. 단계 분해표 — 채워야 할 목록

**이 표의 빈칸이 곧 "누가 무엇을 재야 하는지"의 목록이다.**

| # | 단계 | 오너 | 실행 빈도 | 배분 | 실측 |
|---|---|---|---|---|---|
| A | 카메라 취득 (ISP→버퍼 도착) | 파이프라인 | 매 프레임 | ☐ | — |
| B | 색공간 변환 / GPU 텍스처 업로드 | 파이프라인 | 매 프레임 | ☐ | — |
| C | **① 눈부심 억제** | 알고리즘 팀장 / 구현 파이프라인 | 매 프레임 | ☐ | — |
| D | **② 저조도 개선** | 알고리즘 팀장·모델링 / 구현 파이프라인 | 매 프레임 | ☐ | — |
| E | **③ 탐지 — 전처리** | 모델링 / 통합 파이프라인 | N프레임마다 | ☐ | — |

| C · D | 팀장 알고리즘 확정 → 파이프라인 담당이 셰이더로 구현하며 측정 | §6 요청 4번 이후 |
| E · F · G | 모델 아티팩트 수령 → 파이프라인 담당이 통합하며 측정 | §6 요청 2번 이후 |

### 1-4. 탐지는 왜 비동기여야 하나 — 배분치와 무관한 결론

탐지(YOLO 추론)는 파이프라인에서 **단일 최대 비용 단계**다. 그래서 매 프레임이 아니라 N프레임마다 돈다 — 여기까지는 팀이 이미 같은 방향이다(임베디드 담당 조사 §16도 YOLO만 5~15fps로 따로 뺐다).

문제는 그 다음이다. **N프레임마다 돌리면 그 프레임만 무거워진다.** 가벼운 프레임 여러 장과 무거운 프레임 한 장이 번갈아 나오면:

- 평균 프레임타임은 목표를 통과할 수 있다
- 그러나 **p95는 그 무거운 프레임에 걸린다** — 걷는 사람은 주기적인 끊김으로 체감한다

그래서 탐지를 **별도 스레드로 빼고**, 렌더 경로는 "가장 최근에 완료된 탐지 결과"를 쓴다. 그 사이 프레임은 트래킹이 박스를 이어받는다.

> **이 결론은 각 단계에 몇 ms가 배정되든 성립한다.** 그래서 실측 전에 미리 확정할 수 있는 유일한 구조 항목이고, 이 문서가 지금 시점에 낼 수 있는 가장 단단한 결론이다.
>
> 그리고 **"평균 15FPS"만 목표로 두면 이 문제가 안 보인다.** p95를 목표에 함께 넣자고 제안하는 이유가 이것이다.

## 2. 런타임 파이프라인 — 프레임 1장이 지나가는 길

```
                    ┌─────────────────── 카메라 스레드 ───────────────────┐
  [센서]  →  ① 취득  →  ② 포맷/색공간
                    └──────────────┬───────────────────────────────────┘
                                   │  (프레임 핸들 = GPU 텍스처)
              ┌────────────────────┼─────────────────────────────┐
              ▼                    │                              ▼
  ┌──── 렌더 스레드 (매 프레임) ────┐ │          ┌──── 탐지 스레드 (N프레임마다, 비동기) ────┐
  │ ③ 글레어 억제  (GPU 셰이더)     │ │          │ ⑥ 전처리(letterbox·정규화)              │
  │ ④ 저조도 개선  (GPU 셰이더)     │ │          │ ⑦ YOLO 추론  (ORT Mobile + EP)          │
  │ ⑤ 트래킹 보간  (최근 박스 유지) │◄┼──게시────│ ⑧ 후처리(decode·NMS)                    │
  │ ⑨ 선택적 강조  (오버레이 렌더)  │ │  (최근    └─────────────────────────────────────────┘
  │ ⑩ 디스플레이 합성              │ │   결과)
  └────────────────────────────────┘ │
              │                       │
              ▼                       │
          [출력] ◄────────────────────┘
```

- 렌더 경로는 **탐지 완료를 기다리지 않는다.** 항상 "가장 최근에 완료된 탐지 결과"를 쓴다.
- **트래킹은 IoU 매칭 + 짧은 TTL** 🟡 — KLT 옵티컬플로우는 **고정 카메라 전제**라, 들고 걷는 폰의 큰 전역 모션에서 가정이 깨진다. 팀장 선행 프로젝트(AID)와 밤마실이 갈리는 지점이다.
- **⑨ 강조는 "탐지 박스 내부에서만 엣지 추출"** 🟡 — 임베디드 담당 조사 §9.2 채택. 전체화면 Canny는 저조도 노이즈까지 엣지로 잡아 배경이 폭발한다. 킥오프의 *"세그멘테이션 말고 대형물 + 엣지·경계"* 컨셉과도 맞는다.
- **대가:** 강조 오버레이가 실제 장면보다 **1~2프레임 늦는다.** 허용 여부는 팀 합의가 필요하다.

## 4. 온디바이스 실현 — 추론 가속(EP) 🔴

**팀장 선행 프로젝트(AID)는 NVIDIA GPU + TensorRT 기반인데, 폰에는 NVIDIA GPU가 없다.** 폰에서 ONNX를 가속하는 경로는 아래 셋이고, **SoC(Snapdragon / Exynos / Tensor)마다 최적이 다르며 드라이버 품질 편차가 크다.**

| 순위 | EP | 성격 | 실측 관전 포인트 |
|---|---|---|---|
| 1 | **XNNPACK (CPU)** | 어디서나 동작, 안정 | **베이스라인.** 여기서 바닥을 찍고 시작한다 |
| 2 | **NNAPI** | HW 추상화 (GPU/DSP/NPU) | static shape 필수. 드라이버가 서브그래프를 CPU로 떨구지 않는지 |
| 3 | **QNN (Qualcomm)** | Snapdragon NPU/HTP 직접 | Snapdragon 기기 한정. 최고속 가능성, 기기 종속 |

**이 항목의 결정은 "이 순서대로 실측한다"는 것 자체다.** XNNPACK으로 바닥을 찍고, NNAPI가 실제로 이득인지를 실측 비교로 판정한다. 측정 없이 EP를 고르면 근거가 없다.

> 킥오프에서 나온 **"최신 폰 NPU를 쓰면 된다"**는 방향은 맞다. 다만 **NNAPI/QNN이 실제로 NPU를 잡아주는지는 기기별로 갈린다.** 그래서 §6 요청 1번(기기 기종 취합)이 이 리서치의 최우선 후속이다.

## 5. 입력 경로 추상화 🟡

킥오프에서 시연 방식이 **"사전 비디오 대체 또는 게임 화면으로 제조한 환경 + 오버레이 실시간"**으로 정리됐다. 이건 런타임 구조에 영향이 있어 **PoC 첫날 설계에 넣어야 한다** — 나중에 끼우면 카메라 경로를 다 뜯게 된다.

```
[카메라 (라이브)]   ─┐
[영상 파일 (녹화)]  ─┼─▶ 공통 프레임 소스 ─▶ 이하 파이프라인 동일
[화면 캡처 (게임)]  ─┘
```

세 경로를 **같은 GPU 텍스처 핸들로 정규화**하면 ①②③④는 입력이 무엇인지 몰라도 된다. 얻는 것:

- **발표장 보험** — 조명 때문에 라이브 야간 시연이 불가능할 때 즉시 전환
- **재현 가능한 회귀 테스트** — 같은 영상 = 같은 입력 → 성능·안전 회귀를 숫자로 비교
- **개발 중 야외 촬영 없이 반복 테스트**

출력단(폰 화면 / 글라스)도 같은 방식으로 분리해두면 팀장 보고서의 A·A'·B 3단 구성을 코드 한 벌로 흡수할 수 있다.

> ⚠️ 녹화 경로를 쓰려면 **촬영 규약**이 대량 촬영 **전에** 확정돼야 한다. 규약이 틀린 채로 찍으면 재촬영이 불가능하다. → §6 요청 3번.

## 6. 팀에 요청하는 것

### 1. 팀 전원 — **데모에 쓸 폰 기종 (4명 전부)** ⭐ 최우선

SoC를 모르면 NNAPI/QNN 가능 여부를 못 쓰고, **15FPS 달성 가능성 자체를 말할 수 없다.** §4가 🔴로 막혀 있는 유일한 이유다.

### 2. 모델링 담당 — 모델 export 규약 (아래 3줄이 급함)

통합 학습을 시작하기 전에 맞춰야 한다. **끝난 뒤에 알면 재export다.**

1. **입력 shape 완전 static** (동적 축 금지) — 동적이면 NNAPI/GPU EP가 서브그래프를 못 잡고 통째로 CPU로 떨어진다. F칸이 통째로 무너지는 경로다
2. **NMS 미내장 raw 출력** — ONNX `NonMaxSuppression`은 모바일 EP 대부분이 미지원이라 그래프가 그 지점에서 쪼개지고 텐서가 GPU↔CPU를 왕복한다. 또 conf/IoU 임계값은 **야간 실기기에서** 돌려봐야 하는데, 내장돼 있으면 조정할 때마다 재export가 필요하다
3. **opset 13** — 너무 높으면 모바일 EP 미지원 연산자가 발생한다

> 상세 규약(입력 해상도·정규화·letterbox·출력 텐서 레이아웃·클래스 인덱스·인수 판정용 골든 샘플)은 별도 문서로 배포하겠습니다.

### 3. 촬영하는 모든 사람 — 촬영 규약 3가지

- **야간모드 / HDR OFF** — 최신 폰 나이트모드는 이미 저조도 개선을 해버려서, 우리 ②단계가 개선할 여지가 사라지고 *"폰 기본 카메라로 충분한데 왜 이 앱이 필요한가"*라는 심사 질문을 자초한다
- **30fps 고정(CFR)** — 폰 카메라 기본은 가변 프레임레이트(VFR)라, 그대로 찍으면 프레임 간격이 들쭉날쭉해 **성능 측정 자체가 오염된다**
- **가로 촬영, 회전 메타 0°** — 세로 촬영은 "가로 영상 + 90° 회전 메타"로 저장되어 디코더 출력이 눕는다

### 4. 팀장 — ①②단계 알고리즘 관련 1가지

①눈부심 억제·②저조도 개선이 **픽셀 병렬화 가능한 형태**인지 알려주시면 됩니다. PC 프로토타입이 OpenCV/numpy CPU 기반이어도 괜찮고, **그걸 레퍼런스로 받아 셰이더 포팅은 제가 합니다.** 다만 전역 정렬·큰 커널 순회처럼 병렬화가 어려운 연산이 들어가면 미리 알려주세요 — 설계 단계에서 대안을 찾는 게 쌉니다.

## 8. 마무리 — 이 문서가 한 것과 하지 않은 것

**확정한 것은 하나다.** 탐지를 별도 스레드로 빼는 3스레드 구조. 각 단계에 몇 ms가 배정되든 성립하기 때문에, 실측이 0건인 지금도 확정할 수 있는 유일한 구조 결정이다.

**세운 것은 숫자가 아니라 단위다.** 프레임당 66.7ms, p95 80ms, 연속 10분 — 그리고 그것을 단계별로 나눈 빈칸 표. 지금 팀은 각자 다른 기준으로 "빠르다"를 말하고 있고, 이 문서는 그 기준을 하나로 맞추자는 제안이다.

**일부러 하지 않은 것은 추정이다.** 초안에는 단계별 잠정 ms가 있었으나 전부 지웠다. 실측 0건 상태의 추정치는 (a) 남의 담당 구간에 내가 예산을 배정한 모양이 되고 (b) 나중에 실측과 어긋나면 이 문서 전체의 신뢰를 깎는다. **빈칸을 남기는 쪽이 지금 낼 수 있는 정직한 산출물이다.**

**못 정한 것도 하나다.** 추론 가속(EP). 팀 폰 기종이 모이면 바로 실측에 들어간다.

> 그래서 이 트랙의 현재 상태는 이렇게 요약된다 —
> **구조는 정해졌고, 숫자는 전부 비어 있고, 그 빈칸을 채우는 첫 걸음이 빈 파이프라인 PoC다.**
