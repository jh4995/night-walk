## 1. 🟢 MediaTek 배포 경로 — 상류 표의 빈 행을 채운다

상류 `models/det_c4b_loli0_640/README.md`의 배포 경로 표에는 Snapdragon(QNN/NNAPI) · Exynos(NNAPI) · iOS(CoreML) · PC 뿐이고 **MediaTek 행이 아예 없다.** 우리 측정 기기가 그 표에 없는 SoC다.

### 실측 결과

| arm | 요청 → 해소 | 노드 배치 |
|---|---|---|
| `detect_cpu_prof` | `cpu` → **`cpu`** | `CPUExecutionProvider: 237` |
| `detect_nnapi_prof` | `nnapi` → **`nnapi`** | `CPUExecutionProvider: 10` + **`NnapiExecutionProvider: 11`** |

**통째 폴백이 아니다.** CPU 단독일 때 237개였던 노드가 NNAPI에서 21개로 줄었다 — NNAPI가 그래프 대부분을 흡수해 11개 융합 서브그래프로 만들었다는 뜻이다.

**세 번 독립 재현했다**(그중 마지막이 위 clean 빌드 근거). 판별 수단은 **ORT 프로파일러의 노드별 provider**이고, `getAvailableProviders()`(= 빌드에 컴파일된 목록)로 판단하지 않았다 — 그건 "실제로 쓰였나"에 대해 아무것도 말하지 않는다.

> ⚠️ **`OrtSession`에는 사용 EP를 돌려주는 API가 없다.** 그래서 프로파일러를 켠 **별도 probe 세션**으로 판별하고, 그 사실을 `session.json`의 `resolution_method`에 `(probe session)`으로 문자 그대로 적었다.

### 🟡 그런데 "잡힌다"와 "빠르다"는 다른 질문이다

**11개 파티션은 그 자체로 경고 신호다.** NNAPI가 그래프를 온전히 가져갔다면 융합 노드 **1개**여야 한다. 11개라는 것은 CPU 노드 10개와 번갈아 끼어 있다는 뜻이고, **경계마다 CPU↔NNAPI 텐서 복사가 붙는다.** 그 비용이 가속 이득을 먹으면 NNAPI가 CPU보다 느릴 수도 있다.

**이건 F 실측으로만 답한다.** 이번 라운드가 준 것은 "NNAPI arm을 측정 계획에서 뺄 수 없다"는 사실까지다.

### 🔴 부수 실측 — NNAPI 세션 생성이 매우 비싸다

| | probe 세션 | measured 세션 | 합 |
|---|---|---|---|
| CPU | 73 ms | 58 ms | **0.13초** |
| NNAPI | 13,107 ms | 13,958 ms | **27.1초** |

독립 검증에서 따로 잰 값도 같은 자릿수였다(16.8 + 16.0 = 32.8초). **arm 전환 한 번에 27~33초**, CPU 대비 약 200배다.

측정 창 밖(arm 선택 시점)이라 F를 오염시키지는 않지만 **데모 UX에 직접 걸린다.** 앱 시작 시 NNAPI로 세션을 열면 첫 화면까지 30초가 걸린다는 뜻이다. 배포 구성에서 EP를 NNAPI로 고르면 이 비용을 어떻게 숨길지(스플래시·백그라운드 준비·캐시)가 별도 과제가 된다.

### 이 칸에 쓸 문장

> **MediaTek Dimensity 1080 / Android 16 / ORT 1.28.0** — NNAPI EP가 바인딩된다. 237노드 그래프를 NNAPI 11 융합 서브그래프 + CPU 10 노드로 **분할**한다(통째 폴백 아님). 단 **세션 생성에 약 27초**가 들고, 파티션 경계 비용 때문에 **CPU 대비 속도 우위는 미측정**이다. QNN은 불가(Qualcomm 전용).
> `available_providers` = CPU · NNAPI · WEBGPU · **XNNPACK** (XNNPACK도 이 AAR에 들어 있다 — 세 번째 후보)

**APK 크기:** ORT 이전 2,482,025 B → **31,137,200 B**(arm64-v8a만). ABI 4종을 다 담으면 121,201,115 B라 `abiFilters`로 잘랐다.

## 2. 🔴 팀원1 요청 5건 — **지금 보내는 이유는 리드타임 때문이다**

아래 5건은 **재export나 추가 산출물이 필요**하다. F를 다 재고 나서 재export가 오면 **F를 처음부터 다시 재야 한다.** 입력 해상도가 이미 계약서 640 / 기획서 320 / `data.md` 512로 갈려 있어 그 위험이 가정이 아니다.

### 요청 1 🔴 — 클래스 인덱스를 어느 쪽으로 확정할 것인가

| | 값 |
|---|---|
| `INTERFACES.md` 계약 A-4 | `0 = stairs`, `1 = person` |
| 모델 임베드 메타(`names`) | **`0 = person`, `1 = stairs`** |

모델 바이너리 안의 값을 직접 읽어 확인했다(원문 `{0: 'person', 1: 'stairs'}`).

**런타임은 모델 쪽을 1순위로 쓰고 있고, 계약서를 고치지 않았다.** 계약서는 팀 합의 기록이라 런타임이 임의로 못 바꾸고, 모델은 가중치의 사실이라 코드로 뒤집으면 그게 곧 무음 버그다.

⚠️ **A-4의 불변 규칙이 이 충돌과 정면으로 부딪친다** — *"인덱스는 재배치 금지. 클래스 추가는 항상 끝에 append. 중간 삽입은 이전에 측정한 모든 성능·안전 수치를 무효화한다."*

**그래서 ③→④를 연결하지 않았다.** 연결하는 순간 **사람과 계단의 색이 뒤바뀐다**(계단이 시안, 사람이 노랑). ④ 오버레이에 A-4 기반 `index 0 = stairs` 가정이 이미 들어 있다 — 지금은 정적 더미 박스라 무해하다.

→ **모델을 계약서에 맞출 것인가, 계약서를 모델에 맞출 것인가.** 어느 쪽이든 런타임은 이름으로 매핑하므로 코드 변경은 없다. 다만 **결정 전에는 ④ 강조를 켤 수 없다.**

### 요청 2 🔴 — letterbox `pad` 위치가 아티팩트에 없다

`metadata.json`의 `preprocess.resize`가 `"letterbox (종횡비 유지 + 회색 114 패딩)"` 이라는 **한국어 산문**이고, **`align` 키가 아예 없다.**

계약서 제안값(상하 균등 분배 center)과 Ultralytics 기본이 둘 다 center이므로 **center로 가정하고 진행**하되, 가정임을 코드와 `session.json` 양쪽에 명시해 두었다.

⚠️ 계약서 A-2가 이미 경고한 그대로다 — *"이게 다르면 **박스가 통째로 세로로 밀린다**."* 그리고 이건 **디버깅이 가장 오래 걸리는 실패 모드**다(모델은 "돌긴 도는데 박스가 이상한" 상태가 된다).

→ **center 균등이 맞는지 한 줄 확인 부탁드립니다.**

### 요청 3 🔴 — 사이드카를 기계 판독 가능하게

계약서 A-5는 *"런타임이 이걸 읽고 자기를 설정한다 — 하드코딩 제거"*라고 정했고, 공통원칙 1은 *"런타임은 아무것도 추측하지 않는다"*다. 그런데 지금 `metadata.json`은:

- `preprocess` 블록이 **산문**이라 `scale`·`pad_value`·`align`을 앱이 파싱할 수 없다
- `spec_version` · `model_version`이 **없다** → 조용한 모델 교체를 sha256 외로 탐지할 수 없다
- 임계 키 이름이 계약서 예시(`recommended_thresholds`)와 다르다(**실제는 `inference`**)

→ 다음 export부터 아래 키를 **기계 판독 가능한 형태로** 넣어 주시면 런타임에서 가정을 하나씩 지울 수 있습니다:
```json
"spec_version": "1.0",
"model_version": 4,
"input": { "scale": 0.00392156862, "mean": null, "std": null,
           "letterbox": { "enabled": true, "pad_value": [114,114,114], "align": "center" } }
```

### 요청 4 🔴 — 골든 샘플 1쌍 (계약 §A-6 인수 조건)

계약서가 *"골든 샘플 없는 인수는 없다"*고 정했고, 인수 조건에 **야간 720p 입력 + 그 이미지의 기대 박스(±2px 판정)**가 들어 있다. **현재 미전달이다.**

`metadata.json`의 `parity_check`(24장, 최대 좌표차 0.0001px)는 **상류가 PC에서 PyTorch 대비 확인한 것**이고, **폰 ORT 출력이 그것과 같은지는 별개 문제**다. 같은 입력으로 대조할 수단이 없으므로 **폰 이식 정확성은 영구 미검증**으로 남는다.

→ **§A-6 기준으로 이 아티팩트는 아직 "받았다"가 아닙니다.** 720p 입력 1장 + 기대 박스 JSON 1쌍 부탁드립니다.

### 요청 5 🟡 — PC 기준 추론 시간 참고치 1줄

계약서 A-6의 인수 조건이고, **모바일 F를 놓고 볼 기준선**입니다. 한 줄이면 됩니다.

## 4. 팀 판단이 필요한 것 3건

### 판단 1 — opset 12를 A-1 확정값으로 받는가
계약서 제안값은 13이고 모델은 12다. **낮은 쪽이 모바일 EP 호환에 유리**하므로 실질적으로 문제가 없고, 실제로 NNAPI가 잡혔다. 체크만 하면 된다.

### 판단 2 🔴 — 탐지 주기 N
`FRAME_BUDGET.md` §7 질문 3이 아직 `☐`다. **값을 지어내지 않았다** — `session.json`의 `period_n`은 `null`이다.

대신 **idle-gated 트리거**로 구현할 예정이다: 탐지 스레드가 유휴일 때만 추론하고 바쁘면 건너뛴다. 그러면 **실측 실행 주기**가 관측값으로 나오므로, N을 고르기 전에 "최대로 돌리면 몇 Hz인가"를 먼저 알 수 있다.
⚠️ 그 값은 **상한이지 배포 구성이 아니다** — SoC 경쟁·발열이 최악인 조건이다.

### 판단 3 🔴 — 표시/탐지 경로 분리 추인
`FRAME_BUDGET.md` §3이 2026-08-03에 이미 적어 둔 것이다 — 상류 C7 실측이 분리를 지지하고, 분리되면 **D와 E·F·G가 직렬로 더해지지 않고 병렬(max)**이 된다. **표 구조는 아직 안 바꿨고 팀 추인 대기 상태다.**

이번 라운드는 **그 구조를 선행 구현했다.** 근거는 모델 계약 문서 자신의 경고다:
> *"이 모델의 입력은 ② 저조도 개선을 거치지 않은 **원본 프레임**이다. ②(D1A1+bf)를 탐지 앞단에 붙이면 stairs 야간 오탐이 0.1% → 5.7% 로 **57배**가 된다. 표시 경로(②→④)와 탐지 경로(원본→③)는 분리해서 구현할 것."*

→ **추인이 뒤집히면 이 구조와 측정 arm 설계가 무효가 된다.** 확인 부탁드립니다.

## 5. 아직 못 하는 것 — 미측정을 미측정이라고 쓴다

### 🔴 F칸(추론 비용) — 미측정
이번 라운드는 ORT 세션을 열고 EP를 판별하는 데까지다. `ImageAnalysis`·전처리·프레임당 추론·후처리가 **하나도 붙어 있지 않다.**

⚠️ **이 라운드의 런으로 "탐지를 켜도 프레임타임이 그대로다"를 읽으면 정반대로 틀린다.** 렌더 경로가 `blit_2pass`와 글자 그대로 같으므로 프레임타임도 같은 것이 당연하다. `session.json`의 `round_scope`가 그 사실을 직접 적어 두었다.

**다음 라운드에 잴 것:** E(전처리) / F(추론) / G(후처리)를 각각, `detect_cpu`와 `detect_nnapi`를 **같은 세션에서**, 노이즈 쌍과 함께.

⚠️ **F에는 letterbox 패딩이 포함된다.** 720p는 16:9라 640×360 내용 + 상하 패딩으로 640×640이 되며 **픽셀의 43.75%가 회색 패딩**이다(앱이 계산해 `padding_pixel_fraction`으로 기록한다). 상류도 "세로 패딩만큼 연산이 낭비된다"고 인정하고 있다. **다른 입력 크기의 F와 비교할 때 이 값을 함께 옮겨야 한다.**

⚠️ **F는 CPU 벽시계로 잰다.** GPU timer(`stage_*_ms`)와 **다른 시계**이므로 프레임타임 열이나 GPU 열과 **더하지 않는다.** 하네스가 이 혼입을 import 시점 자기검사로 막는다.

### 🔴 안전 회귀 — 여전히 `evaluated: false`

**탐지가 돌게 되어도 이 값은 false다.** 탐지가 돈다는 것과 안전을 평가했다는 것은 다른 사실이다.

**위험물 강조 누락률을 재려면 셋이 필요하고 우리에겐 없다:**
1. 동일 야간 클립 세트 (계약 C의 녹화 입력)
2. 그 클립의 정답 박스 라벨
3. `models/golden/`의 골든 샘플 (요청 4)

⚠️ 그리고 **`stairs` 재현율은 야간 거리 장면에서 한 번도 측정된 적이 없다** — 상류 held-out 표는 person 클래스 기준이고 stairs 칸은 오탐률뿐이다. ⚠️ 학습 데이터 NightOwls는 **차량 대시캠**이라 보행 시점과 카메라 높이·모션블러가 다르다.

→ **"탐지가 도니까 안전이 확인됐다"로 읽으면 틀린다.**
