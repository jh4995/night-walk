## 0. 한 문단 요약

`.onnx`를 폰에 올려 F(추론) 비용은 이미 쟀지만(보고 B), **그 추론이 옳은 값을 내는지는 아무도
확인한 적이 없었습니다.** 이번에 확인했습니다.

**전처리는 PC와 비트 단위로 같고, 추론은 탐지 판정을 한 건도 바꾸지 않았습니다**
(앵커 201,600개 중 0건). 후처리도 나온 박스 2개가 좌표·신뢰도까지 정확히 일치했습니다 —
다만 **박스 표본이 2개뿐이라 후처리 근거는 얇습니다.**

🔴 **이것은 "모델이 정확하다"가 아닙니다.** 이식이 값을 바꾸지 않았다는 뜻이고,
**mAP·누락률은 여전히 말할 수 없습니다**(정답 라벨이 없습니다).

## 1. 왜 이걸 따로 재야 했나

모델 메타(`metadata.json`)에 `parity_check`가 이미 있습니다 — 24장, 최대 좌표차 0.0001px, 통과.
**그런데 그건 상류가 PC에서 PyTorch ↔ ONNX를 대조한 것입니다.**

우리가 물어야 할 것은 다릅니다:

```
상류가 확인한 것:   PyTorch  ↔  ONNX        (둘 다 PC)
우리가 물어야 할 것: ONNX(PC) ↔ ONNX(폰)     ← 아무도 확인 안 함
```

폰은 arm64이고 PC는 x86-64입니다. 같은 `.onnx`라도 커널 구현·벡터화·연산 순서가 달라
**값이 달라질 수 있습니다.** 게다가 우리 앱은 전처리(YUV→RGB·letterbox)와 후처리(NMS·역변환)를
**Kotlin으로 새로 짰습니다** — 거기서 틀리면 모델이 아무리 좋아도 소용없습니다.

---

## 2. 어떻게 쟀나 — 세 단계를 따로 격리

한 번에 끝까지 비교하면 어긋났을 때 **어디서 어긋났는지 모릅니다.** 그래서 각 단계마다
**앞 단계의 폰 출력을 PC에 그대로 먹여서** 따로 쟀습니다.

```
폰 원본 프레임 ──E(전처리)──▶ 입력 텐서 ──F(추론)──▶ 출력 텐서 ──G(후처리)──▶ 박스
```

| 대조 | PC에 먹인 것 | 폰 쪽 비교 대상 | 격리되는 것 |
|---|---|---|---|
| **E** | 덤프한 원본 YUV 평면 | 폰의 입력 텐서 | 전처리 이식만 |
| **F** | **폰의 입력 텐서** | 폰의 출력 텐서 | 추론만 (E 오차가 안 섞임) |
| **G** | **폰의 출력 텐서** | 폰의 박스 | 후처리만 |

**F가 본진입니다** — 폰 ORT와 PC ORT라는 **독립 구현 둘**의 대조이기 때문입니다.
E·G는 우리가 양쪽 다 짠 코드라 "둘 다 같은 방식으로 틀렸을" 가능성이 남습니다.

### 전제 하나를 기계로 확인했습니다

**폰 ORT 1.28.0 = PC ORT 1.28.0.** `build.gradle.kts`에 적어 둔 문자열이 아니라
`OrtEnvironment.getVersion()`이 런타임에 말한 값입니다. 같은 버전이므로 값이 다르면
**버전 차이가 아니라 빌드/플랫폼 차이**로 좁혀집니다.

## 3. 결과

측정 2세션 · EP 3종 × 4샘플 × 2회 = **샘플 24개**.
샘플은 런 전체에 **10초 간격**으로 흩어 잡았습니다(2세션은 30.3~30.5초에 걸침).

| 단계 | 결과 | 판정 |
|---|---|---|
| **E** 전처리 | **24/24 샘플 비트 단위 일치** (원소 1,228,800 × 24, 불일치 **0**) | 🟢 |
| **F** 추론 | 좌표 채널 max\|차\| **≤ 0.0043 픽셀** · 점수 채널 max\|차\| **≤ 2.6e-06** | 🟢 |
| **F** 안전 지표 | 🔴 **conf 임계 판정이 뒤집힌 앵커 = 0 / 201,600** | 🟢 |
| **G** 후처리 | 박스 **2개** — 둘 다 좌표차 **0.0px** · 신뢰도차 **0.0** · IoU **1.0** | 🟡 표본이 얇다 |

### F는 왜 "비트 일치"가 아닌데 괜찮은가

폰 arm64 빌드와 PC x86-64 빌드는 **비트 단위 일치를 기대하지 않습니다.** 중요한 건 차이의 크기와
**그 차이가 결과를 바꾸는가**입니다.

- 좌표 차이 **0.0043 픽셀** — 720p 프레임에서 1/1000 픽셀 수준. 화면에서 볼 수 없습니다.
- 점수 차이 **2.6e-06** — float32 반올림 수준.
- 🔴 **그래도 "차이가 작다"로는 부족합니다.** 차이가 아무리 작아도 신뢰도가 임계(0.35)
  **바로 위아래**에 있으면 판정이 뒤집혀 **박스 하나가 생기거나 사라집니다.** 그래서
  앵커마다 "폰과 PC가 같은 판정을 했는가"를 세었고, **201,600개 중 0건**이 뒤집혔습니다.

이게 안전 관점의 실제 답입니다.

## 4. 🔴 이 결과로 말하면 안 되는 것

| 말하면 안 되는 것 | 왜 |
|---|---|
| "모델이 정확하다" | 정답 라벨이 없습니다. 이식 정확성과 모델 정확성은 **다른 질문**입니다 |
| "후처리 이식이 검증됐다" | **박스 표본이 2개**입니다. 둘 다 완전히 일치했지만 근거로는 얇습니다 |
| "여러 장면에서 확인했다" | 실내 한 곳입니다. 샘플은 흩어 잡았지만 **장면 다양성은 낮습니다** |
| "탐지가 잘 된다" | 나온 박스 2개가 **둘 다 `stairs` 오탐**입니다(어두운 타일벽) |
| E·F·G의 **시간** | 이 arm은 샘플당 ~7MB를 디스크에 씁니다. **시간 인용 금지**입니다. 비용은 보고 B가 답합니다 |

### 왜 박스가 2개뿐인가

사람이 화면에 있었고 거리도 맞았는데 탐지가 안 됐습니다. 덤프한 입력 텐서를 그림으로 확인한
결과 원인이 셋입니다: **초점이 안 맞음 · 역광 복도(사람이 어두운 쪽) · 이 모델은 야간 실외
대시캠 보행자로 학습됨(실내 복도는 분포 밖)**.

⚠ 그리고 나온 박스 2개는 어두운 타일벽을 `stairs`로 오인한 것입니다 — 모델 계약서가 경고한
*"횡단보도·차선 텍스처를 계단으로 오인"*과 같은 계열입니다.

**이식 대조 관점에서는 오탐도 무방합니다**(같은 코드 경로를 탑니다). 다만 그렇게 얻은 것은
**"코드 경로를 태웠다"이지 "탐지가 정확하다"가 아닙니다.**

## 5. 아직 못 한 것

| # | 무엇 | 막힌 이유 |
|---|---|---|
| 1 | **G 표본 확대** | 실내에서는 한계입니다. 제대로 하려면 **야간 실외 클립**이 필요합니다(`C2`) |
| 2 | **EP 간 직접 대조** | EP마다 런이 따로라 같은 인덱스 샘플이 **다른 프레임**입니다. 출력이 달라도 EP 차이인지 장면 차이인지 못 가릅니다. 각 EP를 PC와 따로 대조해 **간접 근거**로 썼습니다 |
| 3 | **회전 미적용** | 앱이 `rotationDegrees`를 적용하지 않습니다. 이식 정확성 질문은 회전과 **직교**하므로 이 대조는 성립하지만, **탐지 정확도는 애초에 말할 수 없습니다** |
| 4 | **상류 PyTorch 대비** | 상류 레포가 이 저장소에 없습니다. 우리가 대조한 것은 **폰 ↔ PC ONNX**까지입니다 |

**2번이 안전 관점에서 제일 아쉽습니다.** NNAPI가 NPU가 아니라 GPU로 내려간다는 것을 이미
쟀는데(보고 B), GPU 경로는 **fp16으로 떨어질 수 있고** 그러면 같은 입력에 답이 달라집니다.
지금은 "각 EP가 PC와 따로 일치했다"는 간접 근거뿐입니다. 앱이 **한 런에서 세 세션에 같은
텐서를 통과시키면** 직접 답이 나옵니다.

## 6. 팀에 드리는 말

### 팀원1 (모델링)에게

**ONNX export와 폰 이식은 값을 바꾸지 않습니다.** 폰에서 나오는 숫자를 PC 결과와 같은 것으로
보셔도 됩니다. 폰 쪽 전처리(letterbox 중심정렬·패딩 114·BT.601 full range·`/255`)가 PC
재구현과 **비트 단위로 일치**하므로, 상류 파이프라인과 다른 결과가 나온다면 그건 **이식이
아니라 그 위(모델·데이터·임계)** 문제입니다.

⚠ 다만 계약 A 충돌(클래스 순서 등)은 **그대로 남아 있습니다** — 보고 A §2를 봐 주세요.

### 팀원3 (데이터)에게

**야간 실외 클립(`C2`)이 여기서도 필요합니다.** 지금 후처리 이식 근거가 박스 2개인데,
실내에서는 이 모델이 사람을 잡지 못해 더 늘릴 방법이 없습니다.

### 팀 전체에게

**안전 회귀(위험물 강조 누락률)는 여전히 `evaluated:false`입니다.** 이번 대조는 "이식이 값을
바꾸지 않았다"까지이고, **누락률을 재려면 정답 라벨이 필요합니다.** 그건 이 문서가 답한 질문이
아닙니다.
