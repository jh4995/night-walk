## 0. 세 줄 요약

1. **카메라 → ② 저조도 개선 → 화면**, 그리고 **카메라 → ③ 탐지**까지가 **실제 폰에서 동시에 돌아갑니다.**
   각 단계가 몇 ms인지도 다 쟀습니다. 예산표 10칸 중 **7칸이 찼습니다.**
2. 🟢 **15FPS 목표는 지켜집니다.** 추론 1회가 예산의 4배인데도 화면은 **30 FPS**를 유지합니다.
   탐지를 별도 thread로 돌려 화면이 기다리지 않게 만든 설계가 실제로 작동했습니다.
3. 🔴 **마지막 한 칸이 안 이어져 있습니다.** ③이 찾은 것을 ④가 그리려면 **클래스 번호 충돌**을
   먼저 정해 주셔야 합니다 — 지금 연결하면 **계단과 사람의 색이 뒤바뀝니다.**

## 1. 지금 파이프라인이 어디까지 이어졌나

```
카메라 ─┬─ [표시 경로] ② 저조도 개선 ─────────────► 화면        ✅ 동작
        │                                    ▲
        └─ [탐지 경로] ③ YOLO 추론 ──── ✂ ────┘ ④ 강조 표시     🔴 여기가 끊겨 있음
                                        ↑
                              클래스 번호 충돌 (§7)
```

**두 경로를 나눈 이유**는 모델링 담당 측정입니다 — ②를 탐지 앞에 붙이면 계단 오탐이 **0.1% → 5.7%로 57배**가 됩니다. 오인 대상이 횡단보도·차선이라 **저시력 보행자가 반드시 지나는 곳**입니다.
그래서 **탐지는 원본을 먹고, ②는 화면 표시용으로만** 씁니다. 이번 구현이 그 구조입니다.

| 부분 | 상태 |
|---|---|
| 카메라 → 화면 (기본 골격) | ✅ |
| ② 저조도 개선 (Drago · CLAHE · AGCWD · 조합 · bilateral filter) | ✅ 전부 폰에서 돌고 비용도 쟀습니다 |
| ③ 탐지 (ONNX Runtime + 실제 모델) | ✅ 돌아갑니다 |
| ④ 강조 표시 (그리는 것 자체) | ✅ 비용까지 쟀습니다 |
| **③ → ④ 연결** | 🔴 **막혀 있습니다** (§7) |
| ③이 실제로 위험물을 찾는가 | 🔴 **아직 아무것도 못 찾고 있습니다** (§9) |

## 2. 각 단계 비용 — 예산표 10칸 중 7칸

프레임 1장에 쓸 수 있는 예산은 **66.7ms**(15 FPS 기준)입니다.

| 칸 | 무엇 | 실측 | |
|---|---|---|---|
| A | 카메라가 프레임을 주는 주기 | 32.5ms | 비용이 아니라 **주기**입니다 |
| B | 색 변환·GPU 업로드 | 0.63ms | |
| **D** | **② 저조도 개선** | **6.1~7.2** (후보 1개) / **9.3~14.5** (조합) / **22.3** (+bilateral) | §6 |
| **E** | **③ 전처리** | **20.9ms** | 1회당 |
| **F** | **③ 추론** | **251.5 ~ 263.3ms** | 🔴 1회당 |
| **G** | **③ 후처리** | **0.32ms** | 박스 0개 기준 |
| **I** | **④ 강조 표시** | **0.56ms** | 사실상 공짜입니다 |
| C · H · J | ① 눈부심 · 박스 유지 · 화면 합성 | 빈칸 | |

🔴 **E·F·G와 나머지를 더하지 마세요.** 재는 시계가 다릅니다(CPU 벽시계 vs GPU 시계).
🔴 **F는 "1회 추론" 비용이지 프레임당 비용이 아닙니다.** 탐지를 몇 프레임마다 돌릴지가 아직 안 정해져서 환산하지 않았습니다.

## 3. 🟢 15FPS는 지켜집니다 — 그런데 안심할 근거는 아닙니다

5개 조건 **전부 29.88~29.92 FPS**, 느린 프레임 관리선도 통과했습니다. **추론 1회가 예산의 4배인데도** 그렇습니다.

이유는 단순합니다. **탐지를 별도 thread로 돌려서 화면이 탐지 완료를 기다리지 않습니다.** 예산표가 실측 전에 *"탐지는 비동기여야 한다"*고 결론 냈던 것이 맞았습니다.

### 그래서 F가 결정하는 것은 화면 끊김이 아니라 **탐지 갱신 주기**입니다

```
탐지가 갱신되는 주기 = 약 289~300ms  →  초당 3.4번
보행자가 1.4 m/s 로 걸으면  →  탐지와 탐지 사이에 약 42cm 이동
```

여기에 **강조 표시가 1~2프레임 늦게 뜨는 것**이 더 얹힙니다.

> 🔴 **이것이 저시력 보행자에게 허용 범위인지는 성능 문제가 아니라 안전 판단입니다.**
> 예산표 §7 질문 4로 이미 팀에 올려 둔 항목이고, 이제 **실측 근거가 생겼습니다.**

⚠️ **3.4Hz도 최대치입니다.** 탐지 thread가 쉬는 즉시 다음 추론을 걸도록 만들어 재서(가동률 95~97%), **배포 설정이 아니라 "최대로 돌렸을 때"의 값**입니다. 그 조건에서도 화면이 버텼다는 뜻으로 읽어 주세요.

## 4. 🔴 이 기기에서는 CPU가 최선입니다 — 앞 보고를 뒤집습니다

앞 보고에서 *"MediaTek에서 NNAPI가 잡힌다"*고 공유드렸습니다. **속도를 재기 전에 쓴 것이고, 재고 나서 결론이 반대로 갔습니다.**

| 실행 방식 | 추론 1회 | 화면용 GPU 점유율 |
|---|---|---|
| **CPU** | **251.5ms** | **2.2%** |
| NNAPI | 319.3ms (23% 느림) | **43.0%** (최대 97%) |
| XNNPACK | 501.7ms (2배 느림) | — |

**NNAPI는 두 번 나쁩니다.** NPU로 가는 줄 알았는데 **GPU(Mali-G68)로 내려갑니다.** 그래서 자기도 느리고, **화면 처리가 쓰던 GPU까지 빼앗습니다.** 실제로 화면 쪽 느린 프레임 지표가 4.5ms에서 32ms로 **7배** 부풀었습니다 — 예산 66.7ms의 절반입니다.

기기 안에 NPU(MDLA·VPU)가 **있는데도** NNAPI가 그쪽을 안 씁니다.

> ### 배포 경로 표에 넣을 한 줄 (모델 README에 MediaTek 행이 없었습니다)
> **MediaTek Dimensity 1080 / Android 16 / ONNX Runtime 1.28.0 — EP는 `CPU`를 쓴다.**
> NNAPI는 바인딩되지만 NPU가 아니라 GPU로 내려가 23% 느리고 표시 경로를 침해한다.
> 세션 생성만 27초 걸린다. XNNPACK은 2배 느리다. QNN은 Qualcomm 전용이라 불가.

⚠️ XNNPACK은 thread 수를 지정하지 않은 기본값 결과입니다. **값을 지어내지 않았습니다** — 팀이 원하면 정해 주시면 다시 잽니다.

## 5. 🔴 우리 측정 장치 자체에 결함이 있었습니다

②를 재던 중에 **물리적으로 불가능한 숫자**가 나왔습니다 — 1초 동안 1.31초어치의 GPU 작업.

원인은 **단계별로 따로 재서 더하는 방식**이었습니다. 마지막 단계의 마무리 작업이 다음 측정 구간으로 밀려서 **같은 일을 두 번 세고** 있었습니다. 프레임 전체를 한 번에 재는 방식을 따로 만들어 대조해 확정했습니다.

```
단계가 3개일 때   31% 과다
단계가 8개일 때   35% 과다
단계가 9개일 때   43% 과다     ← 단계가 많을수록 커집니다
```

**그래서 지금까지 공유드린 ② 숫자는 전부 실제보다 큰 값입니다.**
예: 조합 `D1A1`은 **14.5ms로 보고했지만 실제는 9.3ms**입니다.

**두 방식을 모두 남겨 뒀습니다.** 단계별 방식만이 "어느 단계가 비싼가"를 말할 수 있고, 전체 방식만이 정확한 총량을 말합니다. **어느 쪽을 기준 문서에 적을지는 팀에서 정해 주셔야 합니다.**

## 6. ② 저조도 — 속도로는 고를 수 없습니다

| 후보 | 폰 GPU 비용 |
|---|---|
| Drago 단독 · CLAHE 단독 · AGCWD 단독 | **6.1 ~ 7.2ms** (셋이 1.1ms 안에) |
| Drago + CLAHE 조합 | **9.3 ~ 14.5ms** |
| Drago + CLAHE + bilateral filter (모델링 담당 1위 후보) | **22.3ms** |

- PC에서 101ms 걸리던 조합이 폰 GPU에서 **22ms**입니다. 모델링 담당 자료의 20ms 기준은 **살짝 넘습니다**(10% 초과).
- ⚠️ 그 20ms 기준은 **기획서에 없는 내부 기준**이고, 우리 예산표의 판정선은 프레임 단위입니다. **팀 합의된 선에 대한 판정이 아닙니다.**
- ⚠️ **경량화 여지를 하나도 안 썼습니다.** 해상도 축소·근사·정밀도 낮추기가 전부 미적용입니다.

**화질은 여전히 판단하지 못하고 있습니다.** 비교할 정답 이미지가 없어서, 우리가 옮긴 것이 원래 알고리즘과 같은 그림을 내는지조차 확인이 안 됩니다.

## 7. 🔴 end-to-end를 막고 있는 것 — 클래스 번호가 반대입니다

| | 값 |
|---|---|
| 계약서 `INTERFACES.md` A-4 | `0 = stairs`, `1 = person` |
| **받은 모델 안의 값** | **`0 = person`, `1 = stairs`** |

모델 파일 안에서 직접 읽어 확인했습니다. 문서 오타가 아닙니다.

**④ 강조 표시는 색이 클래스별로 정해져 있습니다** — 계단은 노랑, 사람은 시안. 빨강을 금지한 것도 *"야간 배경에 묻히고 적록색약에서 무너진다"*는 안전 근거였습니다. **번호를 그대로 믿고 연결하면 계단이 시안, 사람이 노랑이 됩니다.**

> **그래서 ③→④를 일부러 연결하지 않았습니다.** 지금 ④는 고정된 더미 박스를 그리고 있어 무해합니다.
> **모델을 계약서에 맞출지, 계약서를 모델에 맞출지 한 줄만 정해 주시면 바로 잇습니다.**
> 어느 쪽이든 런타임은 이름으로 연결하므로 **코드 변경은 없습니다.**

⚠️ 계약서 A-4에 *"번호 재배치는 이전에 측정한 모든 성능·안전 수치를 무효화한다"*는 규칙이 있습니다. **지금은 탐지 측정치가 0건이라 무효화될 것이 없습니다 — 지금 정하면 공짜입니다.**

## 9. 정직하게 밝히는 한계

### 🔴 탐지 정확도는 이 보고가 아무것도 말하지 않습니다

**모든 런에서 찾은 박스가 0개**였습니다. 확신도가 임계 근처에도 못 갔습니다. 실내 장면인 데다 **화면 회전 보정을 아직 안 넣어서 모델이 옆으로 누운 장면을 보고 있습니다.**
→ 후처리 비용 0.32ms는 **"빈 출력 기준"** 숫자입니다. 박스가 많으면 커집니다.

### 🔴 안전 회귀는 여전히 미평가입니다

**탐지가 돈다는 것과 안전을 확인했다는 것은 다른 사실입니다.** 재려면 (a) 동일 야간 클립 세트 (b) 정답 박스 라벨 (c) 골든 샘플이 필요하고 **셋 다 없습니다.**
⚠️ 그리고 **계단 재현율은 야간 거리 장면에서 한 번도 측정된 적이 없습니다.** 학습 데이터가 차량 대시캠이라 보행 시점과 카메라 높이·흔들림이 다릅니다.

### ⚠️ 그 밖

- **발열이 있습니다.** 진단 런을 6등분하면 추론이 208 → 271ms로 오르고 60~100초쯤에 평탄해집니다. 위 11분 숫자는 평탄 구간을 포함한 값입니다. 조건을 번갈아 배치해 재서 **EP 차이가 발열로 설명되지 않는 것은 확인**했습니다.
- **세션 전후 기기 온도를 기록하지 못했습니다**(제 누락). 다음부터 넣습니다.
- **추론에 letterbox 여백이 포함돼 있습니다.** 720p는 16:9인데 모델은 정사각이라 **픽셀의 43.75%가 회색 여백**입니다. 직사각 입력이 가능하면 해상도를 안 줄이고도 회수할 여지가 있습니다.
- **② 비용은 전부 하한입니다.** 마지막 단계의 마무리가 측정 구간 밖에서 일어나 어떤 방식으로도 못 잡습니다.
