## 1. 프로젝트 개요

- **대회:** 2026 제8회 K-디지털 트레이닝(KDT) 해커톤, 지정과제 「AI 전환 시대, 인간의 역량을 확장하는 디지털 서비스」
- **팀명:** 밤마실 (팀원 4명)
- **아이템:** 야맹증 저시력자의 야간 보행을 돕는 **실시간 AI 시각보조 서비스** (스마트폰)
- **핵심 컨셉:** "균일하게 밝히기"가 아니라 **선택적 시각증강** — 무엇이 위험한지 AI가 판단해 그 경계만 강조, 잔존시력을 가리지 않음
- **4단계 파이프라인:** ① 눈부심 억제(글레어 제어) → ② 저조도 개선(대비 복원) → ③ 위험요소 탐지(YOLO 계열, 계단·보행자) → ④ 선택적 강조(경계 윤곽선)
- **성능 목표:** 720p 기준 15FPS 이상
- **배포:** 스마트폰 단독 **온디바이스** 처리, 영상 서버 전송·저장 없음 (프로토타입: 카메라 입력→처리→화면 출력 라이브 시연)
- **추론:** 모바일 = ONNX Runtime, 엣지/GPU = TensorRT
- **(확장) 계획:** NVIDIA Jetson 엣지 이식, 디스플레이형 글래스 미러링

## 2. 내 역할 (팀원2 재정의: 모바일 런타임·통합 + MLOps)

신청서상 팀원2는 "앱"이지만, 백엔드·인프라·AI 통합 강점을 살리도록 아래로 재정의해서 가져간다.

**내가 오너십 갖는 것**
- 모바일 온디바이스 **런타임**: ONNX Runtime Mobile 등, 네이티브 카메라 → 추론 → 디스플레이 실시간 파이프라인
- 앱 구조 / 서비스 인터페이스 / 입력~처리~출력 연동
- 실기기 **성능 안정화**: 레이턴시·발열·메모리, 15FPS 프레임 버짓 관리
- **모델 검증 자동화 / MLOps**: 팀 공용의 재현 가능한 검증 하네스·CI (팀장의 벤치마크 스크립트를 팀 인프라로 승격)

**넘기거나 나누는 것**
- 순수 UI 폴리싱 → 데모 수준으로 최소화 or 분담
- 검출 모델 설계·학습·튜닝 → 팀원1
- GPU/엣지 추론 최적화 코어 → 팀장 (그의 강점, 아래 참조)
- 야간 촬영·데이터셋·발표자료 → 팀원3

## 4. 기술 기반: 팀장의 선행 프로젝트 "AID"

팀장이 밤마실의 핵심 엔지니어링을 사실상 한 번 완주해본 개인 프로젝트가 있다. (CCTV 영역 침입 탐지)

**AID 구성**
- NVIDIA DeepStream/GStreamer 실시간 GPU 파이프라인, 4채널 동시 처리
- YOLO11s → TensorRT 검출 + NvDCF 트래커
- 침입 판정을 임계값이 아닌 **이벤트 FSM**(OUT → CANDIDATE → IN_CONFIRMED)으로, 다중 프레임 지속 증거로 확정
- 검출 끊김 구간을 **KLT 옵티컬플로우 연속성 + 게이티드 재획득**으로 브리지
- 커스텀 C++ GStreamer 플러그인, 16채널 버스트 벤치마크(단계별 프로파일링, 레이지디코드 최적화 4.9→5.4fps, 가드레일 카운터)

**밤마실로 그대로 전이되는 것**
- YOLO → ONNX/TensorRT export·추론 최적화 (동일 백본)
- 실시간 다단계 GPU 영상 파이프라인 설계·최적화 감각
- 성능 최적화 방법론(단계별 프로파일 → 병목 → 타깃 최적화 → 회귀 검증)
- **트래킹 + KLT 연속성 → 강조 윤곽선 "깜빡임" 방지** (검출이 몇 프레임 놓쳐도 안정적 강조)
- 이벤트 FSM(단일프레임 오검출에 경고 안 띄우고 확정 후 강조)
- 엣지 스택(DeepStream·TensorRT·CUDA) → Jetson 확장 뒷받침

**전이되지 않는 것 / 갭 (주의)**
- **배포 환경이 반대:** AID는 고정 CCTV + 서버/엣지GPU + DeepStream. 밤마실은 움직이는 폰 카메라 1대 + 온디바이스. **DeepStream/GStreamer는 폰에서 안 돌아감** → 모바일은 다른 런타임(ONNX Runtime Mobile / TFLite / 네이티브 카메라)이 필요. 아키텍처·최적화 사고는 넘어오지만 배관 자체는 이식 불가.
- **저조도 개선·눈부심 억제(①②)는 AID에 없음** → 팀 입장 신규 영역
- **카메라 모션:** AID KLT는 고정 카메라 전제. 손에 든 폰은 전역 모션이 커서 옵티컬플로우 가정 일부 붕괴 → 이식 시 튜닝 필요

## 5. 내 작업 라인 기술 스택 (초안 — 확정 아님)

- 추론: ONNX Runtime Mobile (우선), 필요 시 TFLite/NCNN 비교
- 카메라/렌더: 네이티브(Android CameraX / iOS AVFoundation) 또는 크로스플랫폼 검토
- 파이프라인: 카메라 프레임 → 전처리 → 추론 → 후처리(강조 오버레이) → 디스플레이, 프레임 스킵/버퍼링 전략
- 성능: 레이턴시·FPS·발열·메모리 프로파일링, 탐지 모델 2~3프레임 주기 실행 후 트래킹으로 보간
- MLOps: 모델 버전 관리 + 검증 자동화(정확도/FPS 회귀 체크)

## 6. 열려있는 핵심 결정 / 리스크

- **[결정 필요] 프로토타입이 진짜 온디바이스냐, GPU 처리 후 폰 미러링이냐?**
  기획서는 "스마트폰 단독 온디바이스, 서버 전송 없음"을 명시. 그러나 팀장의 편안한 영역은 GPU-서버 DeepStream이라, "일단 GPU 박스에서 돌리고 미러링"으로 흐를 관성이 존재. 모바일 런타임 오너(나)가 이 약속을 지키게 하는 사람. **킥오프에서 먼저 확정할 것.**
- 15FPS 미달 시 대응: 해상도 하향 / 탐지 주기 조정 (기획서 명시) — 실측 후 결정
- ①②단계(저조도·눈부심)를 딥러닝으로 갈지 고전 영상처리로 갈지 — 온디바이스 예산과 트레이드오프
