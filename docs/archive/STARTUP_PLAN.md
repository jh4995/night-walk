# 밤마실 — 새 환경 이식용 착수 플랜

> 이 문서는 팀장의 선행 프로젝트 AID 레포에서 작성됐다. 밤마실은 폰 온디바이스 앱이라 별도 레포로 옮겨 이어간다.
> **사용법:** 이 파일과 아래 §1의 자산들을 새 밤마실 레포로 복사하면, AID 대화 맥락 없이도 팀원2(나)의 작업을 이어받을 수 있다.

## Context

지금까지 AID 레포(`c:\dev\side\AID`, CCTV 침입탐지, DeepStream/GPU) 안에서 밤마실(해커톤 온디바이스
야간 시각보조 앱) 기획·역할 문서를 만들어 왔다. 밤마실은 **폰 온디바이스 실시간 앱**이라 AID의 코드·배관과
다르므로 **밤마실 전용 새 레포**로 옮긴다.

내 긴급 목표는 **킥오프에서 팀원2 역할을 명확히 확정**하는 것이고, 그 다음이 첫 산출물이다.

## 1. 새 레포로 가져갈 자산 (3개 + 이 플랜)

| 파일 (현재 위치) | 역할 | 새 레포에서 |
|---|---|---|

| `KICKOFF_ROLES.md` | 킥오프 결정 3건 + 최종 팀 역할표 + 쉽게 풀어쓴 부록 | **킥오프에서 그대로 사용** |

## 2. 프로젝트 한 줄 브리프 (새 세션용 요약)

- **밤마실**: 야맹증 저시력자의 야간 보행을 돕는 **폰 온디바이스 실시간 AI 시각보조 앱** (2026 KDT 해커톤, 4인).
- **컨셉**: 균일하게 밝히기가 아닌 **선택적 시각증강** — AI가 위험한 것만 판단해 경계선만 강조.
- **4단계**: ①눈부심 억제 → ②저조도 개선 → ③위험 탐지(YOLO) → ④선택적 강조. 목표 **720p 15FPS+**.
- **팀원2(나) = 모바일 런타임·통합·검증 오너**. 상세는 `KICKOFF_ROLES.md`.

## 3. 킥오프에서 확정할 결정 3건 (긴급 목표)

`KICKOFF_ROLES.md`에 근거·원문 인용까지 정리돼 있음. 요지만:

1. **온디바이스 확정** (GPU 서버 미러링 아님) — 신청서가 "서버 전송 없음"을 프라이버시 차별점으로 3회 명시. 근거가 내 편.
2. **①②단계 모바일 실현 = 팀원2** — 알고리즘 설계는 팀장, 폰 위 실현(모바일 GPU)은 나.
3. **검증 분할** — 모델 정확도=팀장/팀원1, **실기기 성능·안전 회귀 + 야간 코스 정량 확인=나** (후자는 신청서상 담당자 미지정 항목을 줍는 것).

**저항 예상 지점:** 결정 3은 신청서상 팀장 칸의 "모델 검증 자동화"를 쪼개는 거라 유일하게 뺏는 모양새.
물러설 선 = 모델 정확도는 넘기고 **실기기 성능 회귀만** 확보.

## 4. 첫 산출물 착수 지침 (새 레포에서 바로 시작)

우선순위 순. 앞 3개는 반나절~1일, PoC는 며칠.

### 액션 0 — 타깃 플랫폼 결정 (선행 블로커)
PoC 스캐폴딩이 이걸로 갈린다. 후보:
- **Android 네이티브** (Kotlin + CameraX + ONNX Runtime Mobile) — AID의 YOLO/ONNX 계보와 가장 직결, 온디바이스 GPU(GLES/Vulkan) 제어 직접적. **기본 추천.**
- **Flutter 크로스플랫폼** — iOS/Android 동시, 그러나 실시간 프레임·GPU 셰이더는 네이티브 채널 필요 → 초기엔 오히려 복잡.
→ 팀 협의로 확정. 결정 전까지 산출물 1~3은 플랫폼 무관하게 진행 가능.

### 산출물 1 — 프레임 버짓 계산표 (반나절, 코드 없음)
"720p 15FPS = 프레임당 66ms"를 단계별로 분해한 표. 카메라취득/①/②/③탐지/④렌더에 예산 ms 배정(빈 칸).
숫자는 아직 몰라도 **팀 공용 언어**가 생김. 미팅 즉효 산출물.

### 산출물 2 — 4단계 모듈 인터페이스 규약 초안 (반나절, 코드 없음)
내가 먼저 빈 템플릿을 채워 배포 → 인터페이스 오너십 선점. 필요한 계약 3개:
- 팀원1→나: 모델 아티팩트 규약 (ONNX opset, 입력 해상도·정규화, 출력 텐서 레이아웃, NMS 내장 여부, 클래스 인덱스)
- 팀장→나: ①②단계 모듈 시그니처 (프레임 in/out 포맷, 색공간, CPU 버퍼냐 GPU 텍스처냐)
- 팀원3→나: 녹화 데모 입력 규약 (컨테이너·코덱·해상도·fps, 어두운 영상 코덱 밴딩 주의)

### 산출물 3 — run_utils.py 이식 (5분, 코드)
`aidlib/run_utils.py`를 밤마실 레포로 복사 → **모든 성능 측정이 git commit + 타임스탬프로 기록**되게 첫날부터 깔기.
MLOps 오너십의 물리적 증거. 측정 시작 전에 깔아야 함.

### 산출물 4 — 빈 파이프라인 PoC ⭐ (며칠, 코드 / 나만 낼 수 있음)
카메라 → 아무 처리 없음 → 화면 + **프레임타임/FPS 오버레이**.
**아무 처리 없는 상태의 베이스라인 숫자 = 전체 프레임 버짓의 분모.** 이 숫자 없이는 팀 목표 정량화 불가.
- (플랫폼=Android 시) CameraX 프리뷰 + 프레임타임 표시. 추론·전처리 없음.
- 확장: 더미 사각형 오버레이(④ 렌더 경로 증명), 녹화영상 입력 경로(팀원3 데모 모드 뼈대).

## 5. AID에서 넘어오는 것 / 안 넘어오는 것 (새 세션 참고)

**개념만 전이 (코드 아님):**
- 2-tier 비용 모델(light path / heavy verifier) → 매 프레임 경량처리 + 탐지는 2~3프레임 주기
- 트랙별 cadence/TTL → 강조 오버레이 갱신 주기 차등
- lazy decode(무거운 일 불필요한 프레임은 준비도 스킵)
- **p95 프레임타임 관리** → 목표를 "평균 15FPS"가 아닌 "평균 15FPS + p95 < 80ms"로
- 성능 튜닝이 안전(위험물 강조)을 굶기지 않았음을 증명하는 가드레일 사고

**코드째 이식:** `run_utils.py` 하나뿐.

**절대 안 넘어옴:** DeepStream/GStreamer 배관, `aidlib/intrusion/*`의 실제 코드(설계는 참고).
AID는 5단계 순차 배치(수십 초)인데 밤마실은 단일 프레임 인-루프 66ms → **런타임은 새로 짠다.**

## 7. Verification (새 레포에서 확인)

- **문서 이식 확인**: 새 레포 루트에 자산(.md 3 + run_utils.py) 존재, `KICKOFF_ROLES.md`가 킥오프에서 그대로 읽힘.
- **run_utils 동작**: 새 레포에서 `init_run()` 호출 시 run_ts 디렉토리 생성, `run_meta.json`에 git commit/dirty 기록되는지(신규 git 레포 초기화 필요).
- **PoC 베이스라인**: 빈 파이프라인 실행 시 화면에 실시간 프레임타임/FPS가 뜨고, 그 수치가 로그로 기록되는지. 이 수치가 이후 모든 버짓 논의의 기준점.
- **킥오프 성과**: 결정 3건이 팀 합의로 확정되고, 신청서 5번 문구 수정(팀원2에 "성능·안전 회귀 검증" 추가) 제안이 반영되는지.
