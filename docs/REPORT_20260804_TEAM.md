# 밤마실 — ② 저조도 **조합**(D1+A1) 실기기 측정 보고

> **누가:** 팀원2 (모바일 런타임·통합·검증) · **언제:** 2026-08-04
> **앞 보고서:** [`REPORT_20260803_TEAM.md`](REPORT_20260803_TEAM.md) — **동결 스냅샷**입니다.
> 그 보고서는 ② 후보를 **하나씩** 쟀고, 이 보고서는 **두 개를 이어붙인 것**을 쟀습니다.
> 숫자는 전부 **Galaxy A34 실기기** 결과이고, 근거 파일 위치를 §10에 적었습니다.

---

## 0. 세 줄 요약

1. **D1(Drago) + A1(CLAHE)을 이어붙인 것을 폰에서 쟀습니다.** 720p에서 **한 장당 +14.5ms**입니다.
   모델링 담당 자료의 "② 20ms 이하" 기준을 **최악 구간(p99)에서도** 통과합니다.
2. **이어붙이는 방식을 두 가지로 만들어 비교했습니다.** 중간 결과를 이미지로 한 번 저장하는
   방식(**체인**)보다, 저장을 건너뛰고 한 번에 처리하는 방식(**융합**)이 **1.73ms 더 쌉니다.**
   측정 잡음의 **42배** 차이라 우연이 아닙니다.
3. 🔴 **그런데 "왜 싸지는가"에 대한 우리 예상이 틀렸습니다.** 착수할 때 적었던 이유("색공간 변환을
   한 번만 하니까")는 **코드와 어긋나 이미 정정된 서술**이었고, 실제 절감은 **중간 이미지 저장을
   없앤 것**에서 나왔습니다. 측정이 정정된 쪽 설명을 지지합니다.

## 1. 무엇을 쟀나

모델링 담당 자료의 표시 경로 잠정 1위는 **`D1A1+bf`** (Drago → CLAHE → bilateral)입니다.
그중 **`D1A1`까지**를 폰 GPU 셰이더로 옮겨 쟀습니다. `bf`(bilateral)는 **안 만들었고 안 쟀습니다.**

이어붙이는 방식이 두 가지 있어서 둘 다 만들었습니다.

| arm | 무엇 | 패스 수 |
|---|---|---|
| **체인** `drago_clahe_chain` | Drago 결과를 **중간 이미지로 저장**하고 그것을 CLAHE에 넣습니다. **PC 코드(cv2)의 동작을 그대로 옮긴 것** | ② 자리 6패스 (전체 8) |
| **융합** `drago_clahe_fused` | 중간 저장을 **건너뛰고** Drago 계산을 CLAHE 안에 집어넣습니다. 🔴 **모델링 담당 자료에 없는 우리 변형** | ② 자리 5패스 (전체 7) |

비교 기준으로 같은 세션에서 **단품 D1**·**단품 A1**·**빈 골격(`blit_2pass`)** 도 다시 쟀습니다.

- 측정 조건: A34 / release 빌드 / 실내 고정 조명 / **폰 삼각대 고정** / 본 측정은 전부 **11분 연속**.
- 두 세션입니다: **08-03 20시 `s4_combo`**(커밋 `8103c2b`, 7런) · **08-04 00시 `s4b_fused`**(커밋 `cdeaffc`, 4런).

## 2. 핵심 숫자

🔴 **열 이름을 반드시 함께 옮겨 주세요.** 아래는 **`gpu_sum_ms`의 arm 간 차분**입니다 —
같은 arm을 **같은 세션의 빈 골격(`blit_2pass`)** 에서 빼서 얻은 값이고, `stage_d_total_ms`가 **아닙니다.**
같은 런에서 어느 열을 보느냐에 따라 **결론이 뒤집힌 전례가 있습니다**(§8-3).

| arm | 세션 (커밋) | **p50** | p95 | p99 | 분석 창 |
|---|---|---|---|---|---|
| **체인 `D1A1`** | 08-03 (`8103c2b`) | **+14.526 ms** | +14.915 | +16.200 | 642.4s |
| **융합** | 08-04 (`cdeaffc`) | **+12.797 ms** | +12.671 | +12.984 | 639.9s |

프레임 처리율은 네 arm 모두 **29.92 FPS**이고 p95 관리선도 통과입니다. 다만 그건
**카메라 공급 주기에 묶인 값**이라 ②의 비용을 말해주지 않습니다(앞 보고서 §6-①과 같은 함정).

## 3. 결론 1 — 융합이 체인보다 **p50 1.729ms 싸다**

```
체인  +14.526 ms
융합  +12.797 ms
      ─────────
차이    1.729 ms   ← 오차 한계 0.041ms의 42배
```

**오차 한계 0.041ms는 이렇게 잡았습니다.**

| 성분 | 값 | 무엇 |
|---|---|---|
| 세션 간 분모 이동 | \|−0.009\| | 같은 `blit_2pass`가 두 세션에서 얼마나 움직였나 (§6) |
| 체인 노이즈 바닥 | 0.032 | 같은 체인 arm을 **연달아 두 번** 재서 나온 실행 간 변동 폭 |
| **합** | **0.041** | |

융합 자신의 바닥(0.009)까지 더해 **0.050**으로 잡아도 **35배**입니다. 신호입니다.

> ⚠️ 다만 두 값은 **세션도 바이너리도 다릅니다**(`8103c2b` vs `cdeaffc`). 그래서 분모를
> 세션마다 다시 재고 그 이동량을 오차 한계에 넣었습니다. 위 42배는 **그 보정을 넣은 뒤의 값**입니다.

## 4. 결론 2 — 🔴 착수 가설의 **메커니즘이 틀렸지만 절감은 실재한다**

단품 두 개를 그냥 더하면 **6.297 + 7.152 = 13.449ms**입니다. 조합은 그 합과 이렇게 다릅니다.

```
단품 합    13.449 ms
체인       14.526 ms   →  합보다 +1.077 비싸다  (이어붙이면 손해가 있다)
융합       12.797 ms   →  합보다 −0.652 싸다    (그 손해를 넘어 이득이 남는다)
```

**착수할 때 우리가 적었던 이유는 틀렸습니다.**

> 착수 근거였던 `RESEARCH_20260803_UPSTREAM.md` §6에 *"두 arm이 색공간(LAB) 변환을 공유하니
> 한 번만 하면 싸진다"* 고 적혀 있었습니다. **그 문장은 코드 대조에서 이미 정정됐습니다** —
> `DragoStage`는 LAB을 **한 번도 쓰지 않습니다.** D1은 **선형 RGB**에서 돌고, LAB의 `L`에서
> 도는 것은 **A1·A2**입니다. 즉 **애초에 공유할 LAB이 없었습니다.**

**앱이 이것을 기계로 확증합니다.** 셰이더 소스 문자열에서 색공간 함수 호출 지점을 세는 계수기를
실어 측정 결과 파일에 함께 남깁니다(`session.stage2_params.color_transform_sites`).
체인 런의 값을 보면 **Drago 패스 3개의 색공간 토큰이 전부 0**이고, 토큰은 CLAHE 패스
두 곳(analyze 8 · apply 9)에만 있습니다. **문서 정정과 코드가 일치합니다.**

**그러면 절감은 어디서 왔나** — 중간 결과를 이미지로 굽는 과정을 없앤 데서 왔습니다.
사람이 센 선언 값(픽셀당·프레임당)이 무엇이 바뀌었는지 말해 줍니다.

| 항목 | 체인 | 융합 | |
|---|---|---|---|
| 중간 이미지 저장 횟수 | 3 | **2** | ← 없앤 것 |
| 전체화면 패스 / 전체 패스 | 6 / 8 | **5 / 7** | ← 없앤 것 |
| 감마 되돌리기(픽셀당) | 2 | **0** | ← 없앤 것 |
| 감마 다시 씌우기(픽셀당) | 1 | **0** | ← 없앤 것 |
| Drago 톤맵 계산(픽셀당) | 1 | **2** | ← **대신 늘어난 것** |
| 선형화 pow(픽셀당) | 2 | **3** | ← **대신 늘어난 것** |
| LAB 정·역변환 | 4 / 3 | 4 / 3 | 안 바뀜 |

즉 **"LAB을 한 번만 해서" 가 아니라 "중간 8비트 이미지를 만들지 않아서"** 절감이 났고,
그 대가로 **톤맵을 픽셀당 두 번** 계산합니다. **재보기 전에는 어느 쪽이 이길지 알 수 없었고,
측정이 융합 쪽이라고 답했습니다.**

## 5. 결론 3 — **720p 조합이 게이트 안이다**

모델링 담당 자료(`data.md`)의 **"② ≤ 20ms" 게이트** — 🔴 **이건 상류(모델링) 기준이고
우리 판정선이 아닙니다.** 우리 판정선은 `FRAME_BUDGET.md` §1과 `lib/targets.py`에만 있습니다.

| arm | p50 | p99 | 상류 게이트 20ms 대비 (p99) |
|---|---|---|---|
| 체인 `D1A1` | +14.526 | **+16.200** | **81.0%** — 통과 |
| 융합 | +12.797 | **+12.984** | **64.9%** — 통과 |

**평균이 아니라 최악 구간(p99)에서도 통과합니다.** 우리 프레임당 예산 기준으로는
체인이 p50 **21.8%** / p99 **24.3%**, 융합이 p50 **19.2%** / p99 **19.5%**를 씁니다
(비율의 분모는 `FRAME_BUDGET.md` §1 · `lib/targets.py`에서 가져왔습니다).

**PC 측정과 나란히 놓을 때 주의할 것:**

```
상류 CPU:  D1A1+bf  720p  101.2 ms
우리 GPU:  D1A1     720p  +14.5 ms   ← 나란히 놓을 수 있는 것은 체인입니다 (같은 알고리즘)
           융합           +12.8 ms   ← 🔴 상류에 없는 우리 변형입니다. 그 자리에 놓지 마세요
```

🔴 **그리고 이것을 "상류 결론을 뒤집었다"로 옮기지 말아 주세요.** 상류 1위는 `D1A1+bf`이고
이후 `+ts`까지 붙었습니다. **`bf`는 우리가 안 쟀습니다.** 말할 수 있는 것은
**"`D1A1`까지는 720p GPU에서 게이트 안"** 까지입니다.

## 7. 🔴 무효 런 하나 — 자동 검사를 **전부 통과한** 실패

08-03 세션의 융합 런 **하나가 무효**였습니다. **승격하지 않았습니다.** 그런데도 여기 적는 이유는
**그 런이 우리 검사를 다 통과했기 때문**입니다. 같은 함정을 다음에 또 밟지 않으려고 남깁니다.

**무슨 일이 있었나.** 융합 셰이더가 A34에서 컴파일에 실패했습니다
(`0:109: S0001: Function call discards 'readonly' access qualifier.`).
앱은 **아무 처리도 안 하는 상태로 폴백**했고, **20,032 프레임 전부**가 그 상태로 돌았습니다.

**🔴 함정은 그 런의 프레임타임이 완벽하게 정상으로 보인다는 것입니다.**

| | 무효 런 | 유효한 체인 런 |
|---|---|---|
| 프레임타임 p50 / p95 / p99 | 32.674 / 38.237 / 40.787 | 32.903 / 38.097 / 40.659 |
| FPS 목표 / p95 관리선 판정 | 통과 / 통과 | 통과 / 통과 |
| 데이터 완전성(`data_complete`) | **true** ← 오히려 더 깨끗해 보입니다 | **false** (8샘플 폐기) |
| 계획 대조 (arm·조명·빌드·시간) | **통과** | 통과 |

아무 처리도 안 했으니 정상인 게 **당연**하고, 폐기 샘플이 0인 것도 **GPU 측정이 애초에 없었기
때문**입니다. 하네스의 모순 검사도 울리지 않았습니다 — 앱이 "GPU 타이머 미지원"이라고
**정직하게 선언**했고 데이터가 그 선언과 일치했기 때문입니다.

**그 런을 무효로 지목한 것은 이 셋뿐입니다.**

| 신호 | 무효 런 | 유효 런 |
|---|---|---|
| 폴백 프레임 수 | **20,032** | 0 |
| CSV의 GPU 열 개수 | **0개** | 7개 |
| 집계된 분포 열 개수 | **1개**(프레임타임뿐) | 11개 |

> **그래서 만든 수동 게이트:** GPU 열이 있어야 하는 arm을 회수한 직후, 출력되는 분포 목록에
> `stage_d_*` 열이 실제로 있는지 **사람이 눈으로 확인합니다. 열이 하나뿐이면 폴백이고,
> 계획 대조를 통과했어도 그 런은 무효입니다.**
> **교훈: 측정 당시의 하네스는 "스피너를 안 바꾼 실수"는 잡지만 "앱 내부 폴백"은 잡지 못했습니다.**

셰이더는 고쳤고 커밋 `cdeaffc`에서 4런을 새로 돌렸습니다. §2의 융합 값은 **그 재측정본**입니다.

## 8. 이 숫자에 반드시 붙는 단서

1. **이 값들은 하한입니다.** 마지막 화면 출력 패스의 마무리 작업이 GPU 측정 창 **바깥**에서
   일어납니다(`GLSurfaceView`를 쓰는 한 옮길 수 없습니다). 실제 비용은 이보다 조금 더 큽니다.
2. 🔴 **세부 열 하나를 그 패스의 비용으로 인용하면 틀립니다.** 어떤 패스의 실행이 다음 패스의
   측정 창에 앉는다는 정량 근거가 결과 파일(`gpu_timer.attribution_note`)에 있습니다.
   **신뢰할 수 있는 것은 합(`gpu_sum`)뿐입니다.** 융합은 패스 경계가 체인과 달라
   **세부 열끼리 체인과 대응시켜 읽지 마세요.**
3. ⚠️ **열을 바꾸면 §4의 부호가 뒤집힙니다.** `stage_d_total_ms`로 같은 계산을 하면
   단품 합 8.798 / 체인 11.570(+2.772) / **융합 9.019(+0.221)** 이라 융합도 합보다 비싸 보입니다.
   `gpu_sum`에서는 −0.652로 반대입니다. 원인은 증분의 상당 부분이 D 열 밖(`gpu_present_ms`,
   arm이 달라도 같은 코드인데 체인 +2.937 / 융합 +3.786 움직입니다)에 앉기 때문입니다.
   **D칸은 `gpu_sum` 차분 쪽입니다**(`FRAME_BUDGET.md` §3 주3). 체인 vs 융합의 **대소는 두 열에서
   같지만**, 단품 합과의 비교는 열에 따라 뒤집힙니다.
4. **분석 창은 프레임 수신 시각의 실제 구간**입니다. `p50 × 표본수`로 유도한 값이 아닙니다
   (과거에 그 유도값을 표에 적었다가 독립 검증에서 잡혔습니다).
5. **노이즈 바닥용 3분 런 4건은 "봉투 점"** 이고 **지속 성능 근거가 아닙니다.** 본 측정은 전부 11분입니다.
6. 🔴 **`D1A1`은 상류 배포 후보가 아닙니다** — 1위는 `D1A1+bf`(+`ts`)이고 **`bf`는 안 쟀습니다.**
7. 🔴 **융합은 이식 최적화가 아니라 알고리즘 변경입니다.** 중간 8비트 양자화가 없어지고,
   감마 왕복이 없어지고(두 곡선이 달라 **상쇄가 아닙니다**), 톤맵을 픽셀당 2회 계산합니다.
   **결과 그림이 PC 레퍼런스와 달라집니다. 채택은 팀장/팀 판단입니다.**
8. 🔴 **이식이 정확한지는 판정할 수 없습니다.** `INTERFACES.md` §B-6 골든 이미지가 없습니다.
   **이 보고서는 비용만 말합니다.**
9. 🔴 **안전 회귀는 측정하지 못했습니다** (`evaluated: false`). ③ 탐지가 없어 위험물 강조 누락률을
