## 2. 정정 ① — `화면 처리 지연 32.7 / 38.1`은 **지연이 아닙니다**

**값 자체는 맞습니다.** 무처리 상태에서 잰 **프레임타임**(프레임이 나오는 간격)이고,
최신 런들에서도 그대로 재현됩니다(실내 p95 **38.07~38.49**, 야간 **38.81~39.05**).

**그런데 이 값은 우리 처리 시간이 아닙니다.** 카메라가 30fps로 프레임을 주는 주기에 묶인
**바닥값**이고, 그래서 **처리 단계를 얹어도 움직이지 않습니다.** `FRAME_BUDGET.md` 주1이
*"예산에서 차감하는 소요 시간이 아니다"* 라고 못 박아 둔 항목입니다.

**진짜 지연은 따로 재고 있고, 이렇습니다:**

| 조건 | 취득~표시 지연 p50 | p95 |
|---|---|---|
| 실내 · 표시 경로만 | **75.6~78.8** | 79.9~82.8 |
| 야간 · 표시 경로만 | **91.3~93.5** | — |
| 실내 · **탐지까지 켠 상태** | — | **91.2~96.9** (표시만은 81.3) |

🔴 **프레임 예산 66.7ms를 이미 넘습니다.** 빈 파이프라인에서도 넘고, 야간에서 +13ms 더
나빠지고, 탐지를 켜면 tail이 더 벌어집니다. 저장소에서 **"프로젝트 최대 위험"** 으로 적어 둔
항목이고 원인 조사는 아직 시작하지 않았습니다.

### 🔴 3.2 하단 판정 문단도 같이 고쳐야 합니다

**현재 문안:**
> 실기기 측정 (Galaxy A34 · NPU 없음)
> 화면 처리 지연 p50 32.7ms · p95 38.1ms · 표시 처리 5.75ms · 연속 구동 10분 이상 —
> 목표 15FPS(≈66ms) 대비 여유 확보.

**제안 문안:**
> 실기기 측정 (Galaxy A34 · **NPU 미활용**)
> 프레임타임 p50 32.7 · p95 38.1ms → **표시 경로 29.9FPS로 목표 15FPS의 2배**,
> 연속 11분 지속(기기 35.1→40.5°C에서도 추론 시간 불변).
> 🔴 **취득~표시 지연은 p50 75.6~78.8ms로 프레임 예산(66.7ms)을 넘는다** — 원인 조사가 다음 과제.

**불리한 숫자를 왜 넣자고 하는가:** 3.2가 이미 *"사전에 정한 기준을 넘지 못하면 기각한다"* 를
우리 차별점으로 내세웠습니다. **같은 절에서 불리한 숫자를 감추면 그 주장 전체가 약해집니다.**
그리고 이 숫자에는 방어가 있습니다 — **표시 경로가 29.9FPS로 목표의 2배**라는 것은
"탐지가 느려도 화면은 안 끊긴다"는 비동기 설계가 실제로 작동했다는 근거입니다.

### 덧붙임: "NPU 없음" → "NPU 미활용"

기기에 NPU가 **있습니다**(`apusys_mdla0` · `apusys_vpu0/1`). 사실은
**"벤더 NNAPI가 그 NPU를 고르지 않아서 못 쓴다"** 이고, 우리가 GPU 점유율을 직접 재서
확인했습니다(§4). 심사위원이 A34 스펙을 찾아보면 걸리는 문장이고,
**정확히 쓰면 오히려 실측 근거가 하나 붙습니다.**

## 3. 정정 ② — `5.75 (무처리)`는 **무처리가 아니고, 인용하면 안 되는 열입니다**

5.757은 **`drago`(② 저조도 개선) 를 켠 arm**의 값입니다. 무처리에서 ② 비용은 **0**입니다.
측정 조건 칸 `실기기 A34(무처리)`가 두 행에 걸쳐 있는데, **위 행에는 맞고 이 행에는 틀립니다.**

**그리고 이 값은 우리가 스스로 인용 금지로 못 박은 열입니다.** ② 비용의 **27%가 다른 열로 새어
나가서** 실제보다 작게 나옵니다(4.58 vs 6.28). 게다가 이 열로 읽으면 **후보 순위가 뒤집힙니다** —
`stage_d_total`로는 agcwd < clahe < drago, 옳은 열로는 agcwd < **drago < clahe**입니다.

**옳은 값:**

| ② 후보 | 하한 | 상한 | 비고 |
|---|---|---|---|
| 단품 3종 (agcwd / drago / clahe) | — | **6.10~7.18** | 속도로는 못 가릅니다 (폭 1.08ms) |
| **조합 D1A1** (체인) | **+9.324** | +14.525 | |
| **조합 D1A1** (융합) | **+9.074** | +12.929 | |
| 조합 + bilateral | +21.030 | +38.169 | |
| **④ 강조 표시** (박스 4개) | **+0.000** | +0.532 | 검출 한계 이하 |

🔴 **배포 구성은 단품이 아니라 조합일 것입니다.** 그러면 표시 비용은 5.75가 아니라
**9~15ms**입니다. **어느 후보를 쓸지는 아직 미확정**이라(§B-6 골든 이미지 대기) 기획서에는
**구간으로 적는 것이 정확합니다.**

## 4. 유효 — 지속 11분은 오히려 **세졌습니다**

| | 기획서 | 최신 실측 |
|---|---|---|
| 지속 실행 | 11분 | **11분 × 6런**, 분석 창 663.1~672.4초 전부 통과 |
| 온도 | (없음) | 🌡 **35.1 → 40.5°C** (전/후 2점) |

🟢 **그리고 이건 5.4 리스크 표에 직접 답합니다.** 그 표의 *"실기기 FPS 미달"* 발생 신호가
**"15FPS 지속 실패 · 10분 후 지연 증가"** 인데, **기기가 5.4°C 오르는 동안 추론 시간이 따라
오르지 않았습니다**(11분 런 4개를 3등분해서 확인: −0.9% ~ +1.0%). 리스크 표에 적어 둔 신호를
**실측으로 반증한 것**이라 넣을 가치가 있습니다.

🟢 **NNAPI 판정도 여기서 나온 실측입니다.** GPU 점유율을 직접 샘플링해서
CPU 2.2% vs NNAPI **43%**(최대 97%)를 확인했습니다 — NNAPI가 추론을 NPU가 아니라 **GPU로
내려서** 자기도 23% 느려지고(319 vs 251ms) 화면 그리는 GPU까지 빼앗습니다.
**3.2 ④번 행(앱측 NMS → NMS-free, "전환 중")과는 다른 이야기**이니 섞이지 않게 봐 주세요.

## 5. 미측정으로 남는 것 — **그대로 "측정 예정"입니다**

**위험 최초 표시 지연**은 여전히 못 쟀습니다. 배관은 어제 생겼습니다(게시 시각 기록 · 표시
단계 계측 · 깜빡임 검출기). 🔴 **막는 것은 도구가 아니라 정답 라벨입니다** — "위험이 화면에
언제 처음 들어왔는가"를 기계가 판정할 기준이 없습니다. 자체 촬영 평가셋이 서면 풀립니다.

⚠️ **관련해서 하나 더:** 기획서 전체에서 **탐지 정확도(mAP·재현율)는 모델 담당 수치**이고,
**앱에서 잰 것이 아닙니다.** 앱은 박스가 나오는 것까지만 확인했고 정답 라벨이 없어
**놓친 위험물 비율은 아직 아무 값도 말할 수 없습니다.** 4.2가 게이트 단계로 설계한 이유와
같은 자리이니, 그 톤은 지금 문서가 이미 맞습니다.
