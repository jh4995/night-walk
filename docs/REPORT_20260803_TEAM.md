## 0. 세 줄 요약

1. **앱 뼈대가 돌아갑니다.** 카메라 영상을 받아 GPU로 처리해서 화면에 뿌리는 파이프라인이 실기기에서 동작하고, **각 처리 단계가 몇 ms 걸리는지 잴 수 있는 계측기**를 붙였습니다.
2. **② 저조도 개선 후보 3개를 전부 폰에서 재봤습니다. 셋 다 비슷하게 빠릅니다** (6.1 ~ 7.2ms, 차이 1.08ms). → **속도로는 못 고릅니다. 화질로 골라야 합니다.**
3. 🔴 **그런데 더 큰 문제를 찾았습니다.** 아무 처리도 안 하는 빈 파이프라인인데도 **지연이 이미 목표를 넘습니다.** ②를 아무리 최적화해도 이건 안 줄어듭니다.

## 1. 제가 맡은 부분

기획서의 4단계 중 **①②③④를 실제 폰에서 돌아가게 만들고, 얼마나 걸리는지 재는 일**입니다.
모델 학습(팀원1)이나 ①② 알고리즘 설계(팀장)는 제 몫이 아니고, **그분들이 정한 것을 폰에 옮기고 측정**합니다.

```
카메라 → ① 눈부심 억제 → ② 저조도 개선 → ③ 위험 탐지 → ④ 강조 → 화면
         └───────── 여기 전체를 폰에서 돌리고 시간을 재는 게 제 일 ─────────┘
```

**목표는 720p에서 15FPS 이상.** 이걸 시간으로 바꾸면 **한 장에 66.7ms 안에 끝내야 합니다.**

## 2. 지금까지 만든 것

### 앱 (Android)

- **CameraX**로 카메라 영상을 받아 → **OpenGL**로 GPU에서 처리 → 화면에 표시.
- ② 알고리즘을 **shader**(GPU에서 도는 작은 프로그램)로 5종류 구현해 두고, **앱 화면에서 골라가며 켤 수 있게** 했습니다. 이걸 arm이라고 부릅니다.

| arm | 무엇 |
|---|---|
| `passthrough` | 아무 처리 없이 그냥 표시 (**비교 기준**) |
| `blit_2pass` | 처리는 없고 GPU 패스 구조만 동일 (**②의 순수 비용을 빼내기 위한 기준**) |
| `gamma_only` | 밝기 곡선만 (②의 최소값) |
| `drago` | **D1** — Drago tone mapping |
| `clahe_gamma` | **A1** — CLAHE + gamma |
| `agcwd` | **A2** — AGCWD |

### 측정 장비 (Python)

- 프레임 한 장 한 장의 시간을 CSV로 기록하고, 백분위(p50/p95/p99)로 요약합니다.
- **`baseline_diff`** — 이전 측정과 비교해 느려졌는지 자동 판정합니다. 조건(기기·조명·arm)이 다르면 **비교를 거부**합니다.
- 모든 측정 결과에 **git commit 도장**이 찍힙니다 → "이 숫자가 어느 코드에서 나왔나"를 나중에도 말할 수 있습니다.
- 승격한 기준 측정 **14건**이 `docs/baselines/`에 저장돼 있습니다.

### 왜 이렇게까지 하나

숫자를 잘못 재면 **팀 전체가 틀린 결정을 합니다.** 실제로 이번에 걸러낸 함정들이 있습니다(§6).

## 3. 🔴 결론 1 — ② 저조도 개선은 **속도로 못 고릅니다**

각 후보를 **11분씩 연속으로** 돌려 측정했습니다.

| 후보 | 프레임 한 장당 추가 비용 | 목표(66.7ms) 대비 |
|---|---|---|
| **A2 `agcwd`** | **6.10 ms** | 9.1% |
| **D1 `drago`** | **6.28 ms** | 9.4% |
| **A1 `clahe_gamma`** | **7.18 ms** | 10.8% |

**차이가 1.08ms밖에 안 됩니다.** 모델링 담당 자료의 "② 20ms 이하만 통과" 기준을 **셋 다 여유롭게 통과**합니다(최대 5.4%).

### 이게 왜 중요한가

모델링 담당이 **PC(CPU)에서** 쟀을 때는 순위가 이랬습니다:

```
CPU:   A1 5.3ms  <  A2 6.2ms  ≪≪  D1 82.9ms   ← D1이 13배 느림
GPU:   A2 6.10   <  D1 6.28   <   A1 7.18ms   ← 거의 같음
```

**D1이 CPU에서 13배 느렸던 게 GPU에서는 사라졌습니다.** 그래서:

> 🔴 **"D1은 너무 느려서 못 쓴다"는 판단은 무효입니다.**
> 상류 문서(`lowlight_classical.md`)가 *"shader로 옮기면 순위가 뒤집힐 수 있으니 기각이 아니라 보류"* 라고 남겨둔 게 정확했습니다.

이게 중요한 이유는 **D1만 눈부심을 실제로 누를 수 있기 때문**입니다. A1·A2는 톤커브가 단조 증가라 구조적으로 밝은 빛을 못 누르는데, 우리 사용자는 **광과민** 야맹증입니다. 상류 자료에서도 *"어느 후보도 단독으로는 목적을 충족하지 못한다"* 며 막혀 있었는데, **D1이 예산 안에 들어오면 그 교착이 풀립니다.**

### 그래서 팀에 필요한 것

**속도가 변별력을 잃었으니 화질로 정해야 하는데, 저는 화질을 판정할 수 없습니다.**

> 🔴 **팀장님 — `INTERFACES.md` §B-6 골든 이미지가 필요합니다.**
> "같은 입력 사진에 대해 결과가 이렇게 나와야 정답"이라는 기준 이미지입니다.
> 이게 없으면 제가 만든 shader가 **의도한 알고리즘과 같은지조차 확인할 수 없습니다.**
> 지금 ②를 고를 근거가 이 저장소에 없습니다.

## 4. 🔴 결론 2 — 진짜 병목은 ②가 아닙니다

**아무 처리도 안 하는 빈 파이프라인**에서 이미:

| | 측정값 | 목표 |
|---|---|---|
| 프레임 간격 | 32.7ms (약 30FPS) | ✅ 여유 있음 |
| 🔴 **지연** (카메라가 빛을 받고 → 화면에 그리기까지) | **75.6 ~ 78.8ms** | ❌ **66.7ms 초과** |
| 🔴 **야간 지연** | **91.3 ~ 93.5ms** | ❌ 더 나쁨 |

**②(6.3ms)를 0으로 만들어도 이 숫자는 안 줄어듭니다.** 카메라가 영상을 주고 화면이 받는 경로 자체에서 시간이 갑니다.

야외 야간 측정에서 **실내보다 13ms 더 느려지는 것**도 확인했습니다. 공급 주기는 똑같은데 **ISP(카메라 이미지 처리 칩)가 프레임을 더 오래 붙듭니다.**

> **제안:** ② 최적화보다 **이쪽을 먼저 파는 게 남는 장사**입니다. 다만 범위가 커서 팀 합의가 필요합니다.

### 관련해서 확인이 필요한 것

한 가지 다행인 발견도 있습니다 — **어두운 곳에서 카메라가 느려질 것이라는 우려는 이 기기에서 사실이 아니었습니다.** 야간에도 30FPS를 그대로 줍니다. 그리고 **11분 연속으로 GPU를 돌려도 발열로 느려지지 않았습니다.**

## 5. 야외 야간에서 눈으로 본 것

⚠️ **이건 측정이 아니라 관찰입니다.** 그래도 남기는 이유는, 지금 ② 화질에 대한 **유일한 증거**이기 때문입니다.

| 관찰 | 내용 |
|---|---|
| **어두운 곳이 더 잘 보였나** | `passthrough` ↔ `drago`를 같은 자리에서 번갈아 보니 **drago 쪽이 더 잘 보였습니다** |
| **화면 깜빡임** | 밝은 곳 → 어두운 곳으로 급히 돌렸을 때 **출렁이지 않고 부드럽게 따라왔습니다** |

🔴 **그런데 이 관찰이 상류 측정과 어긋납니다.** 상류에서는 D1의 어두운 부분 개선 효과를 *"대비배율 1.01배 — 거의 아무것도 못 드러냈다"* 로 쟀습니다. 우리가 D1을 고른 이유도 어두운 부분이 아니라 **눈부심 억제**였습니다.

원인으로 의심되는 것: 독립 검증에서 **우리 shader가 원본보다 계통적으로 더 밝게 나온다**고 측정됐습니다. 즉 **"잘 보인다"의 상당 부분이 진짜 Drago가 아니라 우리 구현의 오차일 수 있습니다.**
→ **이것도 골든 이미지가 있어야 구분됩니다.**

또 **아직 안 해본 상황**이 있습니다: 헤드라이트처럼 **강한 빛이 갑자기 화면에 들어오는 경우**. Drago는 화면에서 가장 밝은 값에 톤커브가 걸려 있어서, 화면 전체가 한 번에 어두워졌다 돌아올 수 있습니다. **미확인입니다.**

## 6. 숫자를 옮길 때 주의할 것 (실제로 걸린 함정들)

측정하다가 **결론이 뒤집히는 함정**을 몇 개 밟았습니다. 회의에서 숫자를 인용하실 때 참고 부탁드립니다.

**① "처리를 얹었는데 FPS가 그대로다" ≠ "공짜다"**
프레임 간격이 카메라 공급 속도에 묶여 있어서, ②를 얹어도 FPS가 안 변합니다. 이건 "비용 0"이 아니라 **"비용이 공급 주기보다 작다"** 는 뜻일 뿐입니다. 단계 비용은 GPU timer로만 말해야 합니다.

**② 어느 열을 보느냐에 따라 순위가 뒤집힙니다**
```
stage_d_total 기준 →  clahe 5.37  <  drago 5.76    (clahe가 싸다)
gpu_sum 차분 기준 →  clahe +7.18  >  drago +6.28    (clahe가 비싸다)
```
**둘 다 맞는 숫자**인데 재는 대상이 다릅니다. **열 이름 없이 숫자만 옮기면 반대 결론이 납니다.**

**③ "CLAHE가 제일 비싸다"는 오독입니다**
CLAHE의 **알고리즘 자체는 셋 중 가장 쌉니다**(1.87ms). 총합에서 뒤지는 이유는 **A1·A2가 공유하는 색공간(LAB) 변환**이 무겁기 때문입니다. **가볍게 만들려면 알고리즘이 아니라 색공간 변환을 손봐야 합니다.**

**④ 측정 조건이 조금만 달라도 값이 움직입니다**
같은 `blit_2pass`를 새벽 2시와 낮 1시에 쟀더니 0.062ms 차이가 났습니다(잡음의 3.9배). 그래서 이번엔 **비교 기준을 후보와 같은 세션에서 다시 쟀습니다.**

## 9. 정직하게 밝혀둘 한계

- **안전 회귀는 측정 못 했습니다.** ③ 탐지가 아직 없어서 "빨라졌는데 위험물을 놓치지 않았나"를 확인할 수단이 없습니다. 모든 결과에 `evaluated: false`로 기록돼 있습니다. **속도만 있는 보고는 불완전한 보고입니다.**
- **②의 비용은 하한입니다.** GPU 마지막 처리의 일부가 측정 창 바깥에서 일어납니다. 실제로는 이보다 조금 더 걸립니다.
- **② 화질은 아직 아무것도 검증 못 했습니다.** 위 숫자는 **비용만** 말합니다.
- **D1(`drago`)만 다른 날 측정**이라 비교 기준이 다릅니다. 같은 기준으로 다시 계산하면 6.28 → 6.34로 움직이지만 **순위는 그대로**입니다.
- **`gamma_only`의 값은 3분 런**이라 10분 지속 조건에서 재확인되지 않았습니다.
