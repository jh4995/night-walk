# 밤마실 기능 개발 표준 루틴

새 기능을 시작할 때 이 순서를 따른다. 이 루틴은 **메인 세션(오케스트레이터)** 이 지키는 것이고,
각 단계 사이는 **사용자 승인 게이트**다. 승인 없이 다음 단계로 넘어가지 않는다.

> **가장 중요한 규칙:** 성능이 걸린 기능이면 **측정 수단을 맨 마지막이 아니라 0단계에서 먼저** 세운다.
> 나중에 만들면, 자동화할 수 있었던 확인을 손으로 반복하게 된다.
> (밤마실이 산출물 1~3(버짓표·계약·하네스)을 코드보다 먼저 만든 것과 같은 사고다.)

---

## 트랙 라우팅

| 트랙 | 범위 | builder | verifier |
|---|---|---|---|
| **android** | `android/` — Kotlin/CameraX/추론/렌더 | `android-builder` | `android-verifier` |
| **harness** | `lib/`, `scripts/` — Python 측정·MLOps | `harness-builder` | `harness-verifier` |

**planner는 하나뿐이고 두 트랙을 다 본다.** 접합부(앱이 남긴 로그를 하네스가 먹는 경로 등)를
보는 유일한 지점이기 때문이다. planner가 트랙을 판정하면 그에 맞는 builder에 위임한다.

---

## 실행 순서

### 0. 준비 — 계약 확인 + 측정 수단 먼저

- **계약 문서를 읽는다** (= source of truth): `INTERFACES.md`, `FRAME_BUDGET.md`, `KICKOFF_ROLES.md`.
- **planner에 독립 위임**한다. 오케스트레이터의 분석을 planner에 입력으로 넘기지 않는다 —
  두 독립 판단이 하나로 붕괴하면 교차검증이 사라진다. planner 계획이 오면 **내 이해와 교차대조**한다.
- **이 시점에 확인한다:**
  - 이 기능이 의존하는 **`☐` 미확정 계약 항목**이 있는가 → 있으면 그 값 없이 진행 가능한
    부분과 막히는 부분을 갈라 놓는다 (병렬 작업의 핵심)
  - 성능이 걸린 기능인가 → 걸렸다면 **측정 스크립트/계측 코드를 먼저** 세운다
- → **[게이트] 계획 승인**

### 1. 구현 — 트랙별 builder

- planner 계획의 트랙 표시대로 `android-builder` 또는 `harness-builder`에 위임.
- 양쪽에 걸치면 **접합부 규격을 정하는 쪽을 먼저** 돌린다.
- Python 편집은 훅이 즉시 구문 검사한다. **Kotlin은 훅이 안 잡는다** — verifier가 처음 잡는다.
- → **[게이트] 구현 결과 확인**

### 2. 계약 검증 — 트랙별 verifier

- **결정적 계약**(인터페이스 일치, 반환 형식, 파이프라인 규약, 스탬프 규약) PASS/FAIL.
- "코드가 스펙대로인가"만 확인한다. **1회면 충분하다.**
- → **[게이트] 검증 통과**

### 3. 성능 baseline 측정 — 성능이 걸린 기능만

- `run_utils` 하네스로 실행 → `outputs/<stage>/<run_ts>/`에 git 스탬프와 함께 저장.
- **평균이 아니라 분포로 본다** (p50/p95/p99). 판정선은 66.7ms / p95 80ms.
- 실기기가 없으면 **"미측정"**으로 기록한다. 합성 데이터 결과는 로직 검증이지 실측이 아니다.

### 4. 튜닝 — baseline diff를 도구로

- 바꿀 때마다 재측정 + **이전 `run_ts` 대비 diff**로 before/after 판정.
- 고칠지 말지는 **숫자로** 정한다. 정적 추측으로 최적화를 늘리지 않는다 (**"안 깨진 것 안 고침"**).
- 변경 전후 측정은 **같은 조건**에서 (같은 기기, 같은 빌드 타입, 같은 지속 시간).
- ⚠️ **성능이 좋아졌다고 보고할 때는 안전 회귀 결과를 함께 낸다.**
  탐지 주기·입력 해상도를 건드렸다면 위험물 강조가 굶지 않았음을 같이 보여야 한다.

### 5. 최종 회귀 + 문서 반영

- verifier 재실행(회귀).
- 실측이 나왔으면 **`FRAME_BUDGET.md`의 해당 칸을 실측값으로 교체**한다.
  이건 팀 합의 문서 수정이므로 **서브에이전트가 아니라 메인 세션에서** 한다.

## 재사용 vs 매번 새로

| 그대로 재사용 | 기능마다 새로 |
|---|---|
| `.claude/agents/` 5종, `.claude/skills/`(nightwalk-conventions, android-runtime, measure-harness, feature-kickoff), `.claude/hooks/check_syntax.py` | 기능별 측정 스크립트, `verify-<대상>` skill(필요해지면), 산출물 문서 |

## 핵심 원칙 3줄

1. **측정 수단을 0단계에서 먼저** 세우고, 성능 판단은 baseline diff로만 (정적 추측 X).
2. **verify = 결정적 계약(1회) / measure = 확률적 분포(N회)** 로 역할을 나눈다.
3. **각 단계 게이트에서 사용자 승인** 후 다음으로.
