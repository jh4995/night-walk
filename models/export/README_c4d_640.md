# ③ 탐지 — 640 비교축 3종 (실기기 속도 계측용) · 2026-08-07

종호님께. **이 파일을 먼저 읽고** 각 zip 안의 `README.md` 로 들어가시면 됩니다.

```
bammasil_det_c4d_11n_640_640.zip   8.8MB   YOLO11n   기준선
bammasil_det_c4d_26n_640_640.zip   8.2MB   YOLO26n   NMS-free  ← 후처리 계약이 다릅니다
bammasil_det_c4d_11s_640_640.zip    32MB   YOLO11s   근거리 정확도 최고
```

전부 **640 고정 · FP32 · 3클래스(`0 person` `1 stairs` `2 bollard`)** 이고,
PT↔ONNX 정합성 검증을 통과했습니다(좌표 최대 0.0002px · conf 최대 3e-05).

해상도는 **640 으로 유지**하기로 했으므로 960 은 넣지 않았습니다.
`c4d_11n_640_noneg` 도 뺐습니다 — `11n_640` 과 아키텍처가 완전히 동일해서
(params 2,590,425 로 같음) 실기기 값이 같게 나옵니다. 데이터 ablation 이지 배포 후보가 아닙니다.

---

## 🔴 먼저: `26n` 은 후처리가 다릅니다

같은 후처리 코드를 세 모델에 돌리면 **26n 만 결과가 깨집니다.**

| | 11n · 11s | **26n** |
|---|---|---|
| 출력 shape | `[1, 7, 8400]` | `[1, 300, 6]` |
| 의미 | 원시 헤드 출력 | **이미 디코딩·정리된 박스 목록** |
| 박스 형식 | `cx, cy, w, h` | **`x1, y1, x2, y2`** |
| 앱이 할 NMS | **필요** (클래스별, IoU 0.7) | **하면 안 됨** (이미 적용됨) |
| 정렬 | 없음 | conf 내림차순 |

26n 에 NMS 를 한 번 더 돌리면 겹치는 정탐이 지워집니다. **모델별로 후처리 분기를 두셔야 합니다.**
자세한 축 구성과 3단계 후처리는 `c4d_26n_640` 패키지의 README 에 있습니다.

## 왜 이 3개인가 — 재는 목적이 각각 다릅니다

- **`11n_640`** — 기준선. 가장 가볍고 현재 배포물(`c4b_loli0`)과 같은 계열이라 인터페이스 변경 0.
- **`26n_640`** — **후처리 비용 제거가 모바일에서 얼마인지**를 봅니다. 정확도로 뽑는 게 아닙니다.
  NNAPI 가 YOLO26 연산자를 받아주는지도 여기서 판명됩니다.
- **`11s_640`** — **근거리 정확도 최고안이 예산에 들어오는지**. params 3.6배(2.6M→9.4M)라
  메모리 대역폭에 걸릴 수 있습니다. 들어오면 640 에서 얻을 수 있는 가장 큰 정확도 상승입니다.

### 데스크톱(RTX) 참고치 — ⚠️ 그대로 믿지 마세요

| 런 | pre | inf | **post** | **합계** |
|---|---|---|---|---|
| 11n_640 | 0.55 | **1.00** | 0.87 | 2.42 |
| **26n_640** | 0.56 | 1.31 | **0.15** | **2.02** |
| 11s_640 | 0.54 | 1.57 | 0.82 | 2.93 |

두 가지를 짚어둡니다.

1. **`inf` 만 보면 순서가 뒤집힙니다.** 26n 은 추론이 31% 느린데 NMS-free 라 후처리가 5.8배
   싸서, **합계로는 26n 이 제일 빠릅니다.** 모바일에선 NNAPI 가 `NonMaxSuppression` 을
   지원하지 않아 11n·11s 쪽에 그래프 분할·CPU 폴백이 생기므로 격차가 더 벌어질 겁니다.
2. **이 `inf` 값들은 애초에 신뢰구간이 넓습니다.** 같은 벤치마크에서 `11n_640`(1.00ms)과
   `11n_640_noneg`(1.28ms)가 **아키텍처가 동일한데 28% 차이**로 나왔습니다. 순수 측정 노이즈입니다.
   **30% 이내 차이는 신호로 보면 안 됩니다.** 노이즈를 확실히 넘는 건 후처리(0.87 vs 0.15)뿐입니다.
   실기기 계측이 필요한 진짜 이유가 이것입니다.

## 계측해주시면 좋을 항목

`inf` 하나만으로는 판단이 안 됩니다. 가능하시면:

- **pre / inf / post / end-to-end 를 분리** — 26n 의 존재 이유가 post 에 있습니다
- **그래프 분할·CPU 폴백 발생 여부** — 11n·11s 의 NMS 가 NPU 에서 떨어져 나오는지
- **p50 뿐 아니라 p95**, 그리고 **10분 연속 구동 시 발열 드리프트**
  (현재 KPI 가 p50 32.7ms / p95 38.1ms / 표시 5.75ms / 연속 11분이라 대조 가능합니다)

26n 은 앱측 NMS 가 준비돼야 의미 있는 수치가 나옵니다.
아직이면 **`11n` · `11s` 두 개만 먼저** 재주셔도 됩니다 — 인터페이스가 동일해서
모델 크기 축만 깨끗이 분리됩니다.

## ⚠️ 정확도 수치는 이 패키지 안에 없습니다

각 패키지 README 의 성능 절에는 "실측치가 등록돼 있지 않다" 경고가 나옵니다. **의도된 것입니다** —

기준이라 여기에 다른 셋의 숫자를 적으면 과대 표기가 됩니다.

정확도는 별도 문서를 보셔야 합니다:

|---|---|

**그리고 그 수치는 전부 주간입니다.** 평가셋(`bollard_val_2146`)이 AIHub 인도보행인데
실측 야간이 0.58% 뿐이라, **야간 볼라드 성능은 아직 측정된 적이 없습니다.**
`person`·`stairs` 의 야간 근거(NightOwls rec34 · StairNet)는 있지만 `bollard` 는 없습니다.
자체 야간 촬영분이 나와야 판정됩니다.
